## 다음에 할 일

적합성 평가(목표 5개 기준: ①②④ 부분 해결, ③⑤ 부족)에서 "한눈에 보이는가"를 기준으로 뽑은 순서입니다. 낭비 경고 잡음 줄이기(포커스·재연결·StrictMode 포함)와 리렌더 시각화, 요청을 보낸 코드 위치는 끝냈습니다(CONTEXT 4.3, 5장).

### 1. 전체 표시 라벨에 지표 붙이기
URL만이 아니라 `×6 · 중복 2 · 같은 응답 3`처럼 보여 줘서 카드 위에서 바로 문제를 알 수 있게 합니다.

### 2. 버튼에 문제 개수와 깜빡임
버튼 테두리 색만으로는 무엇이 문제인지 모릅니다. 개수를 적고, 요청 몰림이나 렌더 폭주가 생기면 잠깐 깜빡입니다.

### 3. 필드 수준 출처
경로가 `$`로만 나오는 경우, 클릭한 글자를 이미 찾은 응답 안에서 다시 찾아 `$.data.summary.total`까지 좁힙니다.

### 4. 요청에서 컴포넌트로 거꾸로 찾기
요청 상세에서 "이 요청을 쓰는 화면"을 누르면 그 응답을 쓰는 박스만 강조합니다.


### 5. React Query 캐시키 설계 감시
React Query는 queryKey로 무효화와 새로고침을 합니다. 키가 잘못 설계되면 캐시를 못 쓰거나 무효화가 빗나갑니다. 다음을 찾아 알려 줍니다.
- 같은 데이터를 서로 다른 키로 중복 캐시하는 경우 (같은 요청, 다른 queryKey)
- `invalidateQueries`에 쓴 키 접두사와 맞는 쿼리가 없는 경우
- 쿼리 함수가 쓰는 값(URL 파라미터 등)이 키에 빠진 경우 (같은 키, 다른 요청)
- `staleTime`이 0이라서 화면을 옮길 때마다 같은 응답을 다시 받는 쿼리

### 6. context 추적: 데이터 출처와 렌더 원인
dev 환경에서는 fiber가 구독하는 context 목록(`fiber.dependencies`)과 그 값을 이전 렌더와 비교할 수 있습니다. 이 정보로 두 가지를 합니다.
- **데이터 출처**: context로만 내려받은 값은 지금 출처를 찾지 못합니다. Provider의 `value`도 훑어서 응답 객체를 찾습니다.
- **렌더 원인 구분**: 지금은 props와 state가 그대로인 렌더를 "부모/context"로 묶습니다. 구독한 context 값이 바뀌었는지 비교해 "부모"와 "context(어느 Provider인지)"로 나눕니다. 고치는 방법이 다르기 때문입니다(부모는 `React.memo`, context는 Provider 나누기나 value `useMemo`).

### 7. 요청 때문에 생긴 렌더 연결
지금 타임라인은 요청과 렌더를 같은 시간축에 나란히 보여 줍니다. 여기서 더 나아가, 응답이 온 직후 그 응답 객체를 받은 컴포넌트가 렌더됐는지 직접 이어서 보여 줍니다. "이 요청이 이 컴포넌트를 N번 렌더시켰다"를 숫자로 보여 주는 것이 목표입니다.
