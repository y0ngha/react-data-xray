# react-data-xray 로드맵

목표와 방법은 [CONTEXT.md](./CONTEXT.md)에 있습니다. 여기서는 아직 하지 않은 일을 우선순위대로 적습니다.

## 다음에 할 일

적합성 평가(목표 5개 기준: ①②④ 부분 해결, ③⑤ 부족)에서 "한눈에 보이는가"를 기준으로 뽑은 순서입니다. 끝낸 것: 낭비 경고 잡음 줄이기(포커스·재연결·StrictMode 포함), 리렌더 시각화, 요청을 보낸 코드 위치, 렌더 이유 분석(context·새 콜백 포함), 요청 ↔ 컴포넌트 ↔ 렌더 연결(CONTEXT 4.3, 4.4, 5장).

### 1. 전체 표시 라벨에 지표 붙이기
URL만이 아니라 `×6 · 중복 2 · 같은 응답 3`처럼 보여 줘서 카드 위에서 바로 문제를 알 수 있게 합니다.

### 2. 버튼에 문제 개수와 깜빡임
버튼 테두리 색만으로는 무엇이 문제인지 모릅니다. 개수를 적고, 요청 몰림이나 렌더 폭주가 생기면 잠깐 깜빡입니다.

### 3. 필드 수준 출처
경로가 `$`로만 나오는 경우, 클릭한 글자를 이미 찾은 응답 안에서 다시 찾아 `$.data.summary.total`까지 좁힙니다.

### 4. React Query 캐시키 설계 감시
React Query는 queryKey로 무효화와 새로고침을 합니다. 키가 잘못 설계되면 캐시를 못 쓰거나 무효화가 빗나갑니다. 다음을 찾아 알려 줍니다.
- 같은 데이터를 서로 다른 키로 중복 캐시하는 경우 (같은 요청, 다른 queryKey)
- `invalidateQueries`에 쓴 키 접두사와 맞는 쿼리가 없는 경우
- 쿼리 함수가 쓰는 값(URL 파라미터 등)이 키에 빠진 경우 (같은 키, 다른 요청)
- `staleTime`이 0이라서 화면을 옮길 때마다 같은 응답을 다시 받는 쿼리

### 5. context로 받은 데이터의 출처
context로만 내려받은 값은 지금 데이터 출처를 찾지 못합니다. 렌더 원인(context 변경)은 구분하게 됐으므로, 같은 `fiber.dependencies` 정보로 context 값 안의 응답 객체도 찾습니다.

### 6. rdx 와 함께 쓰는 AI 스킬
AI 로 빠르게 개발하면 실제 렌더·요청 성능 확인이 빠지기 쉽습니다(CONTEXT 1장의 동기). rdx 보고서(`.rdx/report.json`, `window.__RDX__.report()`)를 근거로 AI 가 스스로 측정하고, 원인을 코드에서 확인하고, 고치고, 다시 재서 확인하도록 돕는 스킬(예: Claude Code 스킬 `rdx-perf`)을 패키지와 함께 냅니다. haiku·sonnet·opus 에게 같은 rdx 출력을 주고 진단시킨 감사(2026-10-27)에서 나온 실수와 부족한 정보를 반영합니다.

**측정하는 법**
- 준비: 앱에 `<RdxDevtools />` 와 dev 서버 플러그인(`react-data-xray/vite` 또는 `middleware`)이 붙어 있는지 확인합니다. 없으면 붙이는 방법을 안내하고 멈춥니다.
- 시나리오: 고칠 화면을 열고 (1) 가만히 둔 상태 30초(폴링·주기 요청), (2) 문제가 된 조작(필터 변경, 탭 이동, 스크롤)을 각각 잽니다. 브라우저 도구가 있으면 AI 가 직접 조작하고, 없으면 사용자에게 할 일을 한 줄씩 요청합니다.
- 수집: 시나리오가 끝날 때마다 `.rdx/report.json`(또는 `window.__RDX__.report()`)을 읽어 시각과 함께 남깁니다. 렌더 감시가 꺼져 있었다면(`renders.monitoring: false`) 다시 잽니다.

**결과를 읽는 법**
- 요청: `duplicates`(2초 안 같은 요청), `sameResponses`(직전과 똑같은 응답), `review`(주기·포커스 재요청)가 큰 엔드포인트부터 봅니다. `callers` 의 함수 이름으로 코드를 찾습니다(줄 번호는 변환된 코드 기준이라 어긋날 수 있습니다).
- 렌더: `avoidable` 이 큰 컴포넌트부터 봅니다. `networkCauses.viaParent` 가 크면 고칠 곳은 그 컴포넌트가 아니라 응답을 받아 setState 한 조상입니다.
- 근거 수준: rdx 출력은 출발점입니다. 모든 진단은 코드에서 확인한 뒤에만 고칩니다(감사에서 한 모델이 "화면 밖 카드도 폴링한다"고 했지만 실제로는 LazyLoad 가 언마운트해 사실이 아니었습니다).

**고칠 수 있는 것(진단 → 처방)**

| 진단 | 처방 |
|---|---|
| 중복 요청(같은 화면에서 두 컴포넌트가 같은 요청) | 공통 조상에서 한 번 받기, React Query 로 옮겨 캐시 공유 |
| 같은 응답 재요청 + 그 응답으로 렌더 | 같은 응답이면 setState 를 건너뛰기, React Query 의 structural sharing, `staleTime` 늘리기 |
| 주기 요청이 숨은 탭·화면 밖에서도 돎 | `document.hidden`·화면 표시 여부로 폴링 멈춤(`refetchInterval` 조건) |
| 부모 렌더로 따라 렌더(`parent`) | 원인 조상의 불필요한 setState 를 먼저 고치고, 그다음 `React.memo` |
| 같은 내용 새 참조(`same-content`) | 부모에서 `useMemo`, 응답을 구조적 공유로 받기 |
| 새 콜백(`new-callback`) | 부모에서 `useCallback` |
| context 변경 | 자주 바뀌는 값과 아닌 값의 context 분리, Provider value 를 `useMemo` |

**지켜야 할 것**
- 동작을 바꾸지 않습니다. 예: `{...data, before: summary}` 처럼 이전 값을 쓰는 화면은 같은 응답일 때 setState 를 건너뛰면 증감 표시가 달라질 수 있으니, 그 값을 쓰는 곳을 먼저 확인합니다.
- 고친 뒤 같은 시나리오로 다시 재서 전후 지표(요청 수, 낭비 수, 줄일 수 있는 렌더 수)를 비교해 보고합니다. 나아지지 않았으면 되돌립니다.
- 앱의 테스트·린트 규칙(해당 저장소의 AGENTS.md 등)을 따릅니다.

**이 스킬을 위해 rdx 에 먼저 필요한 것**(감사에서 세 모델이 공통으로 꼽은 부족한 정보)
- 소스맵을 적용한 호출 위치 줄 번호
- 렌더 행마다 컴포넌트 파일 위치와 "부모를 따라" 렌더의 원인 조상 이름
- 엔드포인트를 호출 위치별로 나눈 집계(`/yard/api` 처럼 여러 화면이 같은 경로를 쓸 때)
- "같은 응답인데 렌더를 일으킨 횟수" 지표
- 전후 비교용 보고서 저장(시나리오 이름을 붙여 `.rdx/` 에 여러 개)

## 배포 전 확인 사항

아직 확인하지 않은 환경입니다. 배포 전에 하나씩 확인하고 결과를 여기에 적습니다.

- [ ] **React 19**: fiber 구조(`dependencies.firstContext`, 훅 체인, `PerformedWork` 플래그), StrictMode 재실행 함수 이름, `__REACT_DEVTOOLS_GLOBAL_HOOK__` 등록 시점이 18과 같은지. React 19 는 `_debugSource` 를 없앴으므로 소스 위치가 필요한 기능은 `_debugStack` 으로 확인
- [ ] **webpack production 빌드**: `process.env.NODE_ENV === 'production'` 분기가 접혀 패널 코드가 번들에서 빠지는지(번들 크기, `react-data-xray` 문자열 검색)
- [ ] **webpack·Next.js dev**: import 순서(react-dom 보다 먼저)가 지켜지는지, 호출 스택 필터가 webpack 의 모듈 경로에서도 rdx 프레임만 빼는지
- [ ] **Vite production 빌드**: rolldown 으로는 확인함(dsi 시절, 41바이트). 리팩터링 뒤 다시 확인
- [ ] **오래된 브라우저**: 컴파일 대상(ES2020)에 맞는지
