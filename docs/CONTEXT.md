# react-data-xray 맥락

이 문서는 rdx를 만든 이유, 풀려는 문제, 정한 방법과 그 이유를 정리합니다. 기능을 고치거나 더할 때 이 문서의 목표와 맞는지 먼저 확인합니다.

## 1. 출발점

**왜 만드는가.** AI로 개발 속도가 빨라지면서 코드는 빠르게 늘지만, 실제 렌더링이나 요청 흐름 같은 성능 검증은 그만큼 따라가지 못합니다. 코드를 한 줄씩 읽어 확인하는 방식으로는 중복 요청, 캐시 누락, 반복 렌더를 놓치기 쉽습니다. rdx는 이것을 **화면에서 바로 보이게(시각화)** 해서, 사람이 빠르게 알아차리고 고칠 수 있게 하려는 도구입니다.

화면에 보이는 컴포넌트의 데이터가 **어느 API 응답에서 왔는지** 알고 싶었습니다. 지금은 Network 탭과 React DevTools를 오가며 값을 직접 맞춰 봐야 합니다. 비슷한 도구를 찾아봤지만 런타임에 "요소 → 컴포넌트 → 요청 → 응답 필드"를 이어 주는 도구는 없었습니다.

- React DevTools: props와 state는 보이지만 출처는 모릅니다.
- TanStack Query Devtools: 캐시와 queryKey는 보이지만 어느 컴포넌트가 쓰는지는 모릅니다.
- react-fetch-tree: 소스를 정적으로 분석해서 실제 응답 값과 연결되지 않습니다.
- Rest API Inspector 같은 네트워크 확장: 요청은 보이지만 컴포넌트와 연결되지 않습니다.

## 2. 목표

rdx는 개발 중인 화면을 보면서 다음 질문에 답하는 도구입니다.

1. **이 컴포넌트는 어떤 API로 그려지는가.** 요청 메서드, URL, 쿼리, payload, 응답 안의 경로까지 보여 줍니다.
2. **데이터가 어떻게 오가는가.** 요청 목록과 시간 흐름을 보여 줍니다.
3. **캐시가 제대로 쓰이는가.** 같은 응답을 다시 받아 오는 요청을 찾습니다.
4. **무분별한 요청이 나가지 않는가.** 중복 요청, 짧은 시간에 몰린 요청을 찾습니다.
5. **요청 때문에 렌더가 반복되지 않는가.** 같은 데이터를 거듭 받거나 요청이 몰려 렌더가 밀리는 것을 보여 줍니다.

## 3. 사용 조건

- **개발 환경 전용.** production 빌드에서는 빈 컴포넌트가 되어 아무것도 하지 않습니다.
- **React 18 이상, 범용.** whatap-front 전용이 아니라 어느 React 앱에서든 씁니다.
- **React Query Devtools처럼 컴포넌트 하나로 붙입니다.** `<RdxDevtools />`를 넣기만 하면 됩니다.
- **데이터 가져오기 방식을 가리지 않습니다.** React Query, SWR, `useEffect` + `fetch`, axios, redux 저장 모두 대상입니다. whatap-front는 React Query와 `useEffect` + `fetch`를 함께 쓰고 있어서 둘 다 필수입니다.
- **쓰기 쉬워야 합니다.** 단축키만으로는 쓰기 어려워서, 드래그로 옮길 수 있는 플로팅 버튼과 패널을 둡니다.

## 4. 방법과 그 이유

### 4.1 응답을 어떻게 잡는가: 네트워크 가로채기

`fetch`, `Response.json/text/clone`, `XMLHttpRequest`, `JSON.parse`를 감쌉니다.

- 라이브러리마다 연동하지 않고 네트워크 단에서 잡습니다. 그래서 React Query, SWR, axios, ky 등이 모두 그대로 잡힙니다.
- axios는 XHR 응답 문자열을 직접 `JSON.parse`합니다. 그래서 응답 문자열을 잠깐 기억해 뒀다가, 같은 문자열이 `JSON.parse`에 들어오면 그 결과를 해당 요청의 응답으로 등록합니다. `res.text()` 뒤에 직접 파싱하는 경우도 같은 방식으로 잡힙니다.
- 자식 컴포넌트의 effect가 부모보다 먼저 실행됩니다. 그래서 가로채기는 컴포넌트 mount가 아니라 **패키지를 import하는 시점**에 설치합니다. 엔트리 파일의 앞쪽에서 import해야 합니다.

### 4.2 컴포넌트와 응답을 어떻게 잇는가: 객체 참조 추적

응답 JSON 안의 모든 객체와 배열을 `WeakMap<객체, {요청, 경로}>`에 등록합니다. 클릭한 DOM에서 React fiber를 찾아 위로 올라가며 props와 훅 state를 훑고, 등록된 객체가 있는지 찾습니다.

- 응답 객체는 React Query 캐시, `useState`, redux store를 거쳐도 **같은 참조로** 전달되는 경우가 많습니다. 그래서 라이브러리와 상관없이 한 방법으로 추적할 수 있습니다.
- WeakMap이라서 응답 객체가 해제되면 같이 사라집니다.

매칭은 세 단계입니다.

| 단계 | 조건 | 생긴 이유 |
|---|---|---|
| 정확 | 같은 참조 | 기본 방법 |
| 파생 | 참조는 다르지만 의미 있는 필드 값 2개 이상이 응답 안의 한 객체와 같음 | whatap-front 프로젝트 목록처럼 redux에 저장하면서 `readable`, `statusTextKey` 같은 필드를 붙인 새 객체를 만드는 경우가 흔했습니다. |
| 추정 | 클릭한 요소의 글자와 같은 값이 응답에 있음 | 위 두 방법으로도 못 찾을 때의 마지막 수단 |

같은 응답 항목(`$.data.projects[3]`)의 하위 객체를 여러 props로 받으면 한 줄로 묶어 보여 줍니다.

React Query의 `QueryObserver`는 모양(`getCurrentResult`, `options.queryKey`)으로 알아보고 queryKey를 함께 보여 줍니다. 패키지에 직접 의존하지 않기 위해서입니다.

### 4.3 낭비 요청을 어떻게 판정하는가

| 판정 | 기준 |
|---|---|
| 중복 요청 | 2초 안에 같은 요청이 다시 나감 |
| 같은 응답 재요청 | 같은 요청의 직전 응답과 본문이 똑같음. 캐시를 쓸 수 있었다는 신호입니다. |
| 요청 몰림 | 500ms 안에 요청 5건 이상 |

위 판정만으로는 polling, StrictMode, 첫 로딩까지 낭비로 잡혀 빨간 표시가 늘 켜져 있게 됩니다. 빨간색이 기본 상태가 되면 아무것도 알려 주지 못하므로, 이유가 있는 반복은 회색으로 따로 나눕니다(`classify.ts`).

| 분류 | 조건 | 표시 |
|---|---|---|
| 중복 요청, 같은 응답 재요청 | 위 판정에 걸리고 아래 어디에도 해당하지 않음 | 빨강(낭비) |
| 주기 요청 | 같은 요청이 3번 이상, 1초 이상의 일정한 간격(중앙값 ±25%)으로 반복 | 노랑(확인 필요) |
| 포커스 재요청 | 창 포커스·탭 전환 직후 1초 안에 같은 응답을 다시 받음(React Query `refetchOnWindowFocus`, SWR `revalidateOnFocus`) | 노랑(확인 필요) |
| 첫 로딩 몰림 | 페이지 진입 후 3초 안의 요청 몰림 | 노랑(확인 필요) |
| StrictMode | 중복이지만 앞선 요청이 취소(abort)됐거나, 호출 스택에 React의 StrictMode 재실행 함수(`commitDoubleInvokeEffectsInDEV` 등)가 있음 | 회색(정상) |
| 재연결 재요청 | 네트워크 재연결(`online`) 직후 1초 안에 같은 응답을 다시 받음 | 회색(정상) |
| 무시 | 사용자가 요청 탭에서 무시로 지정한 엔드포인트(설정 기억) | 회색(정상) |

**진짜 낭비를 숨기지 않기 위한 원칙.** 의도된 동작일 가능성이 높더라도 설정을 점검할 가치가 있는 것(바뀌지 않는 데이터를 자주 polling, 포커스마다 같은 응답, 진입 시 요청 수십 건)은 회색으로 숨기지 않고 노랑으로 남깁니다. 회색은 이유가 확실한 경우만 씁니다.
- StrictMode는 "같은 위치에서 동시에 2건" 같은 추정을 쓰지 않습니다. 같은 위젯 두 개가 동시에 같은 요청을 보내는 진짜 낭비와 구별할 수 없기 때문입니다.
- 포커스·재연결 규칙은 같은 응답 재요청에만 적용합니다. 포커스 직후 여러 곳에서 겹쳐 보낸 중복은 낭비로 남깁니다.
- 간격이 불규칙한 반복(정리되지 않은 interval 등)은 주기 요청으로 보지 않습니다.

플로팅 버튼 테두리, 요청 탭 배지, 전체 표시 박스, 타임라인 막대가 모두 같은 분류를 씁니다.

"같은 요청"은 **메서드 + URL 전체(쿼리 포함) + payload**가 같을 때입니다.

- 같은 엔드포인트라도 쿼리나 payload가 다르면 다른 요청입니다. 쿼리를 빼고 비교했을 때 파라미터만 다른 요청끼리 우연히 응답이 같아도 낭비로 잘못 잡혔습니다.
- 쿼리 파라미터는 순서만 다르면 같은 요청으로 봅니다.
- payload는 문자열, `URLSearchParams`, `FormData`(파일은 이름과 크기)를 비교합니다. `Blob`이나 스트림처럼 바로 읽을 수 없는 본문은 **판정에서 뺍니다.** 확신 없이 낭비로 표시하지 않기 위해서입니다.
- 엔드포인트별 집계는 쿼리를 뺀 "메서드 경로"로 모읍니다. 상대 경로와 절대 경로는 같은 엔드포인트로 합칩니다.

### 4.4 렌더를 어떻게 보는가

React DevTools와 같은 `__REACT_DEVTOOLS_GLOBAL_HOOK__`의 commit 이벤트로 컴포넌트별 렌더 횟수와 commit 시각을 셉니다.

- react-dom은 로드될 때 이 훅에 등록하므로 rdx의 렌더 감시 모듈을 **react-dom보다 먼저** 평가합니다. React DevTools 확장이 없으면 최소한의 훅을 직접 만듭니다.
- 부모가 bailout하면 자식 fiber는 지난 commit의 객체와 플래그가 그대로 남습니다. 같은 fiber 객체면 렌더하지 않은 것으로 봅니다.
- 렌더 감시는 렌더 탭, 타임라인 탭, 전체 표시 중 하나가 켜져 있을 때만 켭니다. 비용 때문입니다.
- rdx 패널 자신의 렌더는 셈에서 뺍니다.

| ⌖ 요소 선택 | 크롬 DevTools의 Cmd+Shift+C처럼 호버 하이라이트 후 클릭합니다. 단축키 Ctrl/Cmd+Shift+D도 됩니다. |
| ▦ 전체 표시 | 응답 객체를 props로 받는 컴포넌트마다 박스와 URL 라벨을 그립니다. 초록은 정확, 파랑은 파생, 빨강은 그 데이터를 준 요청 자체가 낭비로 분류된 경우입니다. 라벨에 최근 10초 렌더 횟수(`↻N`, 10회 이상이면 진한 빨강)를 적고, 렌더될 때마다 박스가 보라색으로 깜빡입니다. 전체 표시가 켜져 있는 동안 렌더 감시도 켜집니다. |
| 데이터 › 출처 탭 | 컴포넌트 경로, 요청, 쿼리, payload, 응답 경로, queryKey, 값, 낭비 표시 |
| 네트워크 › 요청 탭 | 엔드포인트별 호출 수, 중복, 같은 응답, 평균 응답 시간. 전체 기록도 볼 수 있습니다. |
| 네트워크 › 타임라인 탭 | 최근 20초의 요청 막대(호버하면 요약, 클릭하면 상세), 렌더 commit 눈금, 요청 몰림 구간, 실패 요청. 멈춤 버튼으로 화면을 고정합니다. |
| 렌더 › 분석 탭 | 최근 10초 렌더를 컴포넌트 이름별로 묶어 횟수, 자기 렌더 시간, 이유별 횟수(state, props, 같은 내용 새 참조, 부모/context)와 고치는 방법, 연결된 API의 낭비 지표를 보여 줍니다. 줄일 수 있는 렌더순, 횟수순, 시간순으로 정렬합니다. |

### 4.4.1 렌더를 어떻게 줄일 수 있는지 보여 주는가

dev 환경이라 fiber에서 렌더 시점, 렌더 여부, 렌더 시간, 렌더 이유를 모두 알 수 있습니다. 횟수만 보여 주면 "그래서 무엇을 고치나"에 답하지 못하므로, 렌더마다 이전 fiber(alternate)와 비교해 이유를 나눕니다.

**렌더 여부.** React DevTools처럼 이번 commit에서 다시 만든 하위 트리(`fiber.child !== alternate.child`)만 내려가며 `PerformedWork` 플래그를 봅니다. 재사용된 하위 트리에는 지난 렌더의 플래그가 남아 있어 들어가면 오탐이 납니다. 예전에는 "같은 fiber 객체면 렌더 안 함"으로 봤는데, React가 fiber 객체를 재사용하는 경우(형제가 번갈아 업데이트) 렌더 11회 중 1회만 세는 문제가 감사에서 나와 바꿨습니다.

| 이유 | 판정 | 줄일 수 있나 |
|---|---|---|
| mount | 이전 fiber 없음 | 아니요 |
| state | `useState`·`useReducer`·`useSyncExternalStore`(queue가 있는 훅), 클래스 state, `useDeferredValue` 같은 값 훅이 바뀜 | 아니요 |
| context | 읽고 있는 context(`fiber.dependencies`) 값이 바뀜 | `React.memo`로는 안 됨. context 나누기, value `useMemo` |
| props | props 일부가 내용까지 바뀜 | 아니요 |
| 같은 내용 새 참조 | 바뀐 props가 참조만 다르고 내용은 같음(평범한 객체·배열만 JSON 비교, `children`은 빼고 판정) | 예. 부모에서 `useMemo`, 응답을 구조적 공유로 받기 |
| 새 콜백 | 바뀐 props 중 함수가 있고, 나머지는 내용이 같음 | 예. 부모에서 `useCallback` |
| 부모 렌더 | props·state·context가 그대로인데 부모가 렌더돼서 같이 렌더됨 | 예. `React.memo`(이미 memo인 컴포넌트는 세지 않음) |

렌더 시간은 React dev 빌드가 기록하는 `selfBaseDuration`(자식을 뺀 자기 자신의 렌더 시간)을 씁니다. 렌더 › 분석 탭은 기본으로 "줄일 수 있는 렌더"가 많은 순으로 정렬하고, 컴포넌트마다 이유별 횟수와 고치는 방법을 보여 줍니다. 전체 표시 박스 라벨에도 `↻N(불필요 M)`을 적습니다.

### 4.4.2 렌더와 네트워크를 어떻게 잇는가

렌더는 네트워크와 관계없이 일어날 수도 있습니다. 그래서 둘을 근거가 있을 때만 잇고, **네트워크와 무관한 비효율 렌더도 똑같이 보여 줍니다.**

- **렌더 → 네트워크.** 렌더마다 원인을 붙입니다.
  - 직접: 새로 바뀐 state·props·context 안에 응답 객체가 있고, 그 응답이 렌더 직전 3초 안에 도착함. 시간 조건은 예전 응답 데이터를 담은 채 다른 이유로 state를 바꾼 경우(`setState({...prev, filter})`)를 걸러 내기 위한 것입니다.
  - 부모를 따라: 같은 commit에서 네트워크 응답 때문에 렌더된 가장 가까운 조상을 따라 렌더됨. 자기 state가 바뀐 렌더는 조상을 이어받지 않습니다.
  - 렌더 › 분석 탭에 "네트워크 응답으로 N회 · 네트워크와 무관 M회"를 나란히 보여 주고, 원인 요청을 누르면 요청 상세가 열립니다.
- **네트워크 → 컴포넌트.** 요청이 보이는 곳(요청 목록, 타임라인 막대, 렌더 탭의 원인 요청 등)에 호버하면, 그 요청의 응답 객체를 props·훅 state로 들고 있는 컴포넌트를 화면에서 주황 점선으로 강조합니다. 요청 상세에는 "이 요청의 데이터를 쓰는 컴포넌트" 목록이 나옵니다. React Query는 응답이 같으면 이전 객체를 재사용하므로, 같은 요청(메서드·URL·payload)의 이전 응답까지 함께 찾습니다.

### 4.5 요청 상세를 어떻게 보여 주는가

dev 환경 전용이라 요청과 응답의 원문을 보관해도 됩니다. 요청 헤더(`fetch`의 `init.headers`, XHR의 `setRequestHeader`), 응답 헤더, 응답 원문(텍스트 계열만, 요청당 최대 100KB)을 남깁니다. SSE, ndjson 같은 스트리밍 응답은 끝까지 버퍼링하지 않도록 원문을 읽지 않습니다. 실패, 취소, 타임아웃된 요청도 에러와 함께 기록합니다.

## 6. 알려진 한계

- React 내부 구조(fiber, 훅 체인, 플래그)는 공개 API가 아닙니다. React가 구조를 바꾸면 깨질 수 있습니다.
- 파생 매칭은 필드 값 겹침으로 판단해서, 같은 값을 가진 다른 응답을 가리킬 수 있습니다.
- context로만 내려받은 값은 아직 추적하지 못합니다.
- 최근 요청 200건만 기억합니다.
- 렌더 수는 React 내부 플래그로 세므로 실제와 조금 다를 수 있습니다.
- "같은 내용 새 참조"는 JSON으로 비교하므로 Map, Set, 클래스 인스턴스, 순환 참조, 20KB를 넘는 값은 다르다고 봅니다(줄일 수 있는 렌더를 놓칠 수 있음).
- 클래스 컴포넌트의 `forceUpdate`는 "부모 렌더"로 분류됩니다.
- 렌더의 네트워크 원인은 응답 객체를 그대로 쓸 때만 찾습니다. 응답을 가공해 새 객체로 만들면(map, select 등) 네트워크와 무관으로 보일 수 있습니다.
- 요청 헤더는 비교하지 않습니다. 헤더만 다른 요청은 같은 요청으로 봅니다.
- 주기 요청은 같은 요청이 3번 쌓여야 알아봅니다. 그 전까지(첫 두 번)는 낭비로 보일 수 있습니다.
- StrictMode 재실행 확인은 effect 안에서 바로(await 전에) 요청을 보낼 때만 됩니다. await 뒤에 보내면 호출 스택에 React 함수가 남지 않아 중복으로 잡힙니다.
- React Query의 structural sharing 때문에 다시 받아 온 데이터라도 바뀌지 않은 객체는 처음 요청이 출처로 표시됩니다.
- 응답 경로가 `$`(응답 전체)인 정확 매칭은 "이 API 어딘가"라는 뜻입니다. 숫자 하나만 props로 받는 컴포넌트는 필드까지 좁히지 못합니다.

## 7. 개발 기록

- 패키지 위치: `~/Project/react-data-xray`. 커밋은 개인 계정으로 합니다.
- whatap-front 테스트: `.worktrees/rdx` 워크트리(브랜치 `local/react-data-xray`)에 `file:` 의존성으로 붙여 확인합니다. whatap-front 쪽 변경은 커밋하지 않습니다.
- 패키지를 고치면 `pnpm build` 후 whatap-front의 `node_modules`에 dist를 복사하고, dev 서버를 `--force`로 다시 띄웁니다. 같은 버전으로 덮어쓰면 브라우저 캐시에 이전 모듈이 남으므로, 그 모듈 URL을 `cache: 'reload'`로 한 번 받아 둔 뒤 새로고침합니다.
- 감사 기록: 코드 감사(구현과 문서 대조)와 문제 해결 적합성 평가를 서브에이전트로 따로 했습니다. 코드 감사에서 나온 버그(파생 매칭 기준, 이전 fiber 트리 읽기, 오버레이 비용, XHR 재사용, 스트리밍 버퍼링, 경로 접두사 비교, 렌더 첫 commit 과다 집계, webpack production 잔존)는 고쳤습니다. 적합성 평가의 개선 제안은 ROADMAP에 넣었습니다.
