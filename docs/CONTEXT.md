# react-data-xray 맥락

이 문서는 rdx를 만든 이유, 풀려는 문제, 정한 방법과 그 이유를 정리합니다. 기능을 고치거나 더할 때 이 문서의 목표와 맞는지 먼저 확인합니다.

## 1. 출발점

**왜 만드는가.** AI로 개발 속도가 빨라지면서 코드는 빠르게 늘지만, 실제 렌더링이나 요청 흐름 같은 성능 검증은 그만큼 따라가지 못합니다. 코드를 한 줄씩 읽어 확인하는 방식으로는 중복 요청, 캐시 누락, 반복 렌더를 놓치기 쉽습니다. rdx는 이것을 **화면에서 바로 보이게(시각화)** 해서, 사람이 빠르게 알아차리고 고칠 수 있게 하려는 도구입니다.

화면에 보이는 컴포넌트의 데이터가 **어느 API 응답에서 왔는지** 알고 싶었습니다. 지금은 Network 탭과 React DevTools를 오가며 값을 직접 맞춰 봐야 합니다. 비슷한 도구를 찾아봤지만 런타임에 "요소 → 컴포넌트 → 요청 → 응답 필드"를 이어 주는 도구는 없었습니다.

- React DevTools: props와 state는 보이지만 출처는 모릅니다.
- TanStack Query Devtools: 캐시와 queryKey는 보이지만 어느 컴포넌트가 쓰는지는 모릅니다.
- react-fetch-tree: 소스를 정적으로 분석해서 실제 응답 값과 연결되지 않습니다.
- Rest API Inspector 같은 네트워크 확장: 요청은 보이지만 컴포넌트와 연결되지 않습니다.

## 2. 목표

rdx는 개발 중인 화면을 보면서 다음 질문에 답하는 도구입니다.

1. **이 컴포넌트는 어떤 API로 그려지는가.** 요청 메서드, URL, 쿼리, payload, 응답 안의 경로까지 보여 줍니다.
2. **데이터가 어떻게 오가는가.** 요청 목록과 시간 흐름을 보여 줍니다.
3. **캐시가 제대로 쓰이는가.** 같은 응답을 다시 받아 오는 요청을 찾습니다.
4. **무분별한 요청이 나가지 않는가.** 중복 요청, 짧은 시간에 몰린 요청을 찾습니다.
5. **요청 때문에 렌더가 반복되거나 화면이 밀리지 않는가.** 같은 데이터를 거듭 받거나 요청이 몰려 렌더가 밀리는 것, 그리고 응답이 도착해 화면이 밀리는 것(레이아웃 이동)처럼 사용자가 보는 결과까지 보여 줍니다(4.4.3).

## 3. 사용 조건

- **개발 환경 전용.** production 빌드에서는 빈 컴포넌트가 되어 아무것도 하지 않습니다.
- **React 18 이상, 범용.** whatap-front 전용이 아니라 어느 React 앱에서든 씁니다.
- **React Query Devtools처럼 컴포넌트 하나로 붙입니다.** `<RdxDevtools />`를 넣기만 하면 됩니다.
- **데이터 가져오기 방식을 가리지 않습니다.** React Query, SWR, `useEffect` + `fetch`, axios, redux 저장 모두 대상입니다. whatap-front는 React Query와 `useEffect` + `fetch`를 함께 쓰고 있어서 둘 다 필수입니다.
- **쓰기 쉬워야 합니다.** 단축키만으로는 쓰기 어려워서, 드래그로 옮길 수 있는 플로팅 버튼과 패널을 둡니다.
- **AI 가 읽을 수 있어야 합니다.** 사람이 화면에서 보는 결과를 AI 도 보고서(`.rdx/report.json`, `window.__RDX__`)로 읽고 고칠 수 있게 합니다.
- **측정 대상 앱을 느리게 하지 않습니다.** 개발 도구가 메인 스레드를 차지하면 측정이 틀어지므로, 비싼 일은 나눠 하고 화면 갱신은 DOM 에 직접 씁니다(4.10).

## 4. 방법과 그 이유

### 4.1 응답을 어떻게 잡는가: 네트워크 가로채기

`fetch`, `Response.json/text/clone`, `XMLHttpRequest`, `JSON.parse`를 감쌉니다.

- 라이브러리마다 연동하지 않고 네트워크 단에서 잡습니다. 그래서 React Query, SWR, axios, ky 등이 모두 그대로 잡힙니다.
- axios는 XHR 응답 문자열을 직접 `JSON.parse`합니다. 그래서 응답 문자열을 잠깐 기억해 뒀다가, 같은 문자열이 `JSON.parse`에 들어오면 그 결과를 해당 요청의 응답으로 등록합니다. `res.text()` 뒤에 직접 파싱하는 경우도 같은 방식으로 잡힙니다.
- 자식 컴포넌트의 effect가 부모보다 먼저 실행됩니다. 그래서 가로채기는 컴포넌트 mount가 아니라 **패키지를 import하는 시점**에 설치합니다. 엔트리 파일의 앞쪽에서 import해야 합니다.

### 4.2 컴포넌트와 응답을 어떻게 잇는가: 객체 참조 추적

응답 JSON 안의 모든 객체와 배열을 `WeakMap<객체, {요청, 경로}>`에 등록합니다. 클릭한 DOM에서 React fiber를 찾아 위로 올라가며 props와 훅 state를 훑고, 등록된 객체가 있는지 찾습니다.

- 응답 객체는 React Query 캐시, `useState`, redux store를 거쳐도 **같은 참조로** 전달되는 경우가 많습니다. 그래서 라이브러리와 상관없이 한 방법으로 추적할 수 있습니다.
- WeakMap이라서 응답 객체가 해제되면 같이 사라집니다.

매칭은 세 단계입니다.

| 단계 | 조건 | 생긴 이유 |
|---|---|---|
| 정확 | 같은 참조 | 기본 방법 |
| 파생 | 참조는 다르지만 의미 있는 필드 값 2개 이상이 응답 안의 한 객체와 같음 | whatap-front 프로젝트 목록처럼 redux에 저장하면서 `readable`, `statusTextKey` 같은 필드를 붙인 새 객체를 만드는 경우가 흔했습니다. |
| 추정 | 클릭한 요소의 글자와 같은 값이 응답에 있음 | 위 두 방법으로도 못 찾을 때의 마지막 수단 |

같은 응답 항목(`$.data.projects[3]`)의 하위 객체를 여러 props로 받으면 한 줄로 묶어 보여 줍니다.

React Query의 `QueryObserver`는 모양(`getCurrentResult`, `options.queryKey`)으로 알아보고 queryKey를 함께 보여 줍니다. 패키지에 직접 의존하지 않기 위해서입니다.

### 4.3 낭비 요청을 어떻게 판정하는가

| 판정 | 기준 |
|---|---|
| 중복 요청 | 2초(`configure` 의 `dedupeWindowMs`) 안에 같은 요청이 다시 나감 |
| 같은 응답 재요청 | 같은 요청의 직전 응답과 본문이 똑같음. 캐시를 쓸 수 있었다는 신호입니다. |
| 요청 몰림 | 500ms 안에 요청 5건 이상(`burst`) |
| 항목마다 보낸 요청(N+1) | 1초(`nPlusOne.windowMs`) 안에 같은 엔드포인트(ID 를 `:id` 로 묶은 경로)로 같은 보낸 컴포넌트(모르면 같은 호출 위치)가 서로 다른 ID 요청을 5개(`nPlusOne.count`) 이상 보냄. 무시한 엔드포인트는 표시하지 않음. 노랑(확인 필요)이며 낭비로 세지 않습니다 |

위 판정만으로는 polling, StrictMode, 첫 로딩·화면 이동까지 낭비로 잡혀 빨간 표시가 늘 켜져 있게 됩니다. 빨간색이 기본 상태가 되면 아무것도 알려 주지 못하므로, 이유가 있는 반복은 회색으로 따로 나눕니다(`classify.ts`).

| 분류 | 조건 | 표시 |
|---|---|---|
| 중복 요청, 같은 응답 재요청 | 위 판정에 걸리고 아래 어디에도 해당하지 않음 | 빨강(낭비) |
| 주기 요청 | 같은 요청이 3번 이상, 1초 이상의 일정한 간격(중앙값 ±25%)으로 반복. 한 주기보다 훨씬 이른 요청(끼어든 재조회)은 건너뛰고, 훨씬 늦은 간격(탭 숨김으로 멈춤)에서는 구간을 새로 잇는다. 이어진 구간의 요청이 기록의 70% 이상일 때 구간의 요청만 주기 요청이다. 구간 밖 요청끼리 또 일정하게 3번 이상 이어지면(박자가 바뀜) 주기로 보지 않는다 | 노랑(확인 필요) |
| 포커스 재요청 | 창 포커스·탭 전환 직후 1초 안에 같은 응답을 다시 받음(React Query `refetchOnWindowFocus`, SWR `revalidateOnFocus`) | 노랑(확인 필요) |
| 화면 진입 몰림 | 몰림의 500ms 창 가운데 페이지 진입 후 3초 안에 시작한 창, 또는 화면 이동이 [창 시작 − 3초, 창의 마지막 응답 + 1초] 안에 있는 창. 화면 이동은 `pushState`·`replaceState`·`popstate`·`hashchange` 뒤 pathname(해시 라우터면 `#/…`·`#!/…` 경로까지)이 바뀐 것입니다. 쿼리만 바뀐 것, 페이지 안 앵커(`#section`)는 이동이 아닙니다. | 노랑(확인 필요) |
| staleTime 경과 재조회 | React Query 가 staleTime 이 지나 다시 받았고 응답이 같음(`stale-elapsed`) | 노랑(확인 필요) |
| 무효화 뒤 재조회 | 무효화해서 다시 받았지만 바뀐 것이 없음(`after-invalidate`) | 노랑(확인 필요) |
| StrictMode | 중복이고 호출 스택에 React의 StrictMode 재실행 함수(`commitDoubleInvokeEffectsInDEV` 등)가 있음. 또는 앞선 요청이 취소(abort)됐고, 두 요청이 200ms 안에 같은 commit 순번에서 나갔고, 겹친 무효화가 그 요청을 취소한 것이 아니고, 보낸 컴포넌트가 그 commit(useLayoutEffect 면 다음 commit)에서 마운트됐고 그 commit 뒤 2초 안에 나감. 그 commit 에 렌더 기록이 없으면(감시를 켜기 전 첫 마운트) 마운트 조건은 보지 않음 | 회색(정상) |
| 재연결 재요청 | 네트워크 재연결(`online`) 직후 1초 안에 같은 응답을 다시 받음 | 회색(정상) |
| 무시 | 사용자가 요청 탭에서 무시로 지정한 엔드포인트(설정 기억), 또는 코드의 `configure({ ignore })` 에 든 엔드포인트(이름이나 정규식, 패널에서 풀 수 없음) | 회색(정상) |

**진짜 낭비를 숨기지 않기 위한 원칙.** 의도된 동작일 가능성이 높더라도 설정을 점검할 가치가 있는 것(바뀌지 않는 데이터를 자주 polling, 포커스마다 같은 응답, 진입 시 요청 수십 건)은 회색으로 숨기지 않고 노랑으로 남깁니다. 회색은 이유가 확실한 경우만 씁니다.
- StrictMode는 "같은 위치에서 동시에 2건" 같은 추정을 쓰지 않습니다. 같은 위젯 두 개가 동시에 같은 요청을 보내는 진짜 낭비와 구별할 수 없기 때문입니다.
- 포커스·재연결 규칙은 같은 응답 재요청에만 적용합니다. 포커스 직후 여러 곳에서 겹쳐 보낸 중복은 낭비로 남깁니다.
- 간격이 불규칙한 반복(정리되지 않은 interval 등)은 주기 요청으로 보지 않습니다. 10초 주기가 5초로 바뀌는 것처럼 박자가 바뀐 반복도 interval 이 겹쳐 돈 신호라 주기로 보지 않습니다. 반대로 간격 하나가 어긋났다고 그 요청의 기록 전체를 빨강으로 바꾸지는 않습니다(끊김 하나는 허용 오차를 넓혀도 못 잡습니다).
- 취소(abort)만으로는 StrictMode 로 보지 않습니다. React Query 는 마지막 관찰자가 빠질 때, 겹친 무효화는 앞 재조회를, 다시 받기 핸들러와 AbortController 를 쓰는 검색 입력은 앞 요청을 취소합니다. StrictMode 는 마운트할 때만 effect 를 두 번 돌리므로, 취소는 마운트한 commit 직후의 요청일 때만 근거로 씁니다(마운트 뒤 2초가 지나 핸들러가 보낸 요청은 아닙니다). 보낸 컴포넌트를 모르면 근거가 아닙니다. 다만 앱의 첫 마운트는 RDX 버튼이 렌더 감시를 켜기 전이라 그 commit 의 렌더 기록이 없습니다. 이때만 간격·순번·취소로 판단합니다(이 판단은 유휴 큐에서 정해 기록에 담습니다).
- 화면 이동은 일어난 그때 기록합니다(`capture/navigation.ts`). 감싼 `pushState`·`replaceState` 는 원래 메서드를 같은 `this`·인자로 먼저 부르고 그 반환값을 돌려준 뒤, 바뀐 `location` 을 읽어 기록합니다. 기록이 실패해도 앱에는 알리지 않습니다. Navigation API 의 `navigate` 는 이동이 확정되기 전(취소·다운로드 포함)에 오므로 쓰지 않습니다. 요청 기록의 `route` 로 이동을 짐작하지 않는 것은, 이동 뒤 첫 요청이 늦게 나가면(정적 화면) 그 뒤의 낭비 몰림까지 진입이 되고, 해시 라우터는 pathname 이 바뀌지 않기 때문입니다.
- 창의 마지막 응답 1초 뒤까지 이동을 기다리는 것은 데이터 라우터(React Router loader, Next.js App Router 의 RSC 요청)가 새 화면의 응답을 받은 뒤에 주소를 바꾸기 때문입니다. 요청 시작이 아니라 응답 끝에서 재므로 백엔드가 느려도 진입으로 봅니다. 그 대가로 낭비 몰림 직후 1초 안에 화면을 옮기면 그 몰림도 노랑이 되지만, 숨기지 않고 타임라인에 남습니다. 같은 이유로 버튼은 창의 응답이 모두 끝나고 1초가 지난 뒤에 판정하므로 낭비 몰림 깜빡임은 최대 1초 늦습니다. 창이 시작하고 1초가 지났는데 몰림이 1초 넘게 이어지면 응답을 기다리지 않고 알립니다(끝나지 않는 반복).
- 진입인지는 몰림 전체가 아니라 500ms 창마다 봅니다(`analyzeBursts`). 겹치는 창을 합친 몰림 전체로 판정하면, 화면 이동 직후 시작한 끝나지 않는 반복이 끝까지 진입으로 남고, 끝 시각이 계속 늘어 버튼이 판정할 때를 얻지 못합니다. 합친 몰림은 그리기용이며 진입·낭비가 바뀌는 창에서 잘라 구간으로 나눕니다. 이동에 걸친 몰림은 걸친 창이 모두 진입이라 한 진입 구간이 됩니다. 이미 알린 창에서 이어지는 창은 같은 몰림으로 보고 다시 깜빡이지 않습니다.
- 몰림은 페이지(`load`)마다 따로 찾고, 새로고침 전 페이지에서 되살린 기록(`restored`)은 세지 않습니다. 이 페이지의 이동 기록과 맞춰 볼 수 없고, 새 페이지의 첫 요청과 이어 붙으면 안 되기 때문입니다.
- 몰림과 변경 뒤 재조회는 보고서에도 싣습니다(`requests.bursts`·`followUps`, #74). 패널과 다른 말을 하지 않도록 버튼·타임라인의 `analyzeBursts` 와 요청 상세의 `followUps` 를 그대로 부르고, 무시도 같은 판정(`IgnoreMatcher`)으로 따릅니다. 무시한 엔드포인트의 요청은 반복만이 아니라 첫 요청까지 몰림에서 뺍니다(버튼·타임라인도). 의도된 반복(폴링·비콘)으로 지정한 엔드포인트가 몰림을 만들면 무시가 무시가 아니기 때문입니다. 변경 뒤 재조회는 한 조회를 바로 앞(응답이 가장 늦게 끝난) 변경 요청 하나에만 붙여 두 저장 사이의 조회를 두 번 세지 않고, 페이지 로드마다 한 번에 구해(O(n log n)) 5초 주기 업로드에서도 변경 요청 수만큼 다시 훑지 않습니다. 같은 응답은 분류와 같이 다른 페이지 로드의 응답과 같은 것은 세지 않고, 새로고침 전 기록은 몰림처럼 보지 않습니다. 변경이나 재조회 쪽 엔드포인트를 무시한 쌍은 수를 그대로 두고 `ignored` 로 표시합니다. summary 는 낭비 몰림과, 같은 응답을 받은 변경 뒤 재조회(polling·무시 제외)만 medium 으로 짚습니다. 몰림은 원인을 말해 주지 않는 묶음이라, 같은 요청을 이미 센 구체적인 finding(중복·같은 응답·N+1) 뒤에 두고 그 요청을 절감에서 빼며, 그런 요청이 절반 이상이면 몰림 대신 그 finding 들의 `relatedFindings` 에 몰림을 답니다.
- N+1(#85)은 몰림과 따로 판정합니다. 몰림은 여러 엔드포인트가 섞여 원인을 말해 주지 않습니다. 같은 ID 의 반복은 중복 판정이 맡으므로 서로 다른 ID 만 세고, 중복으로 판정된 요청은 넣지 않습니다. 보낸 컴포넌트를 모르면 호출 위치(스택 앞쪽 3줄)로 묶고, 그것도 모르면(스택이 끊김) 짚지 않습니다. 가상화 목록처럼 의도된 경우가 있어 노랑으로 두고 배지는 세지 않습니다. 판정은 유휴 큐에서 합니다. 보낸 곳(annotate)·중복 판정·응답 세 step 이 모두 끝난 기록만 패턴별 색인(시작 시각 순)에 넣고, 마지막 step 이 그 기록이 든 창만 봅니다(창 안의 수만큼). 어느 step 이 늦어도 빠지지 않게 하려는 것입니다. 무시는 패널에서 바뀔 수 있어 판정에는 넣지 않고, 보고서·패널이 같은 무시 판정(`IgnoreMatcher`)으로 표시에서 뺍니다.
- 버튼과 타임라인은 같은 함수로 같은 판정을 씁니다. 대상(scope)으로 좁힌 타임라인도 전체 기록으로 판정한 뒤 대상 요청이 든 구간만 그리므로 버튼과 어긋나지 않습니다. 타임라인은 20초 창 밖에서 시작한 구간을 창 안으로 자르고 보이는 요청만 셉니다.

플로팅 버튼 테두리, 요청 탭 배지, 전체 표시 박스, 타임라인 막대가 모두 같은 분류를 씁니다.

**쓰지 않는 응답(`unused`, 노랑).** 위 분류는 반복을 보지만, 아무도 쓰지 않는 데이터를 받는 요청(남은 코드, 받아 두고 버리는 prefetch)은 Network 탭에서 정상으로 보입니다. 응답이 오고 3초 뒤(응답 → setState → 렌더가 끝날 시간) 유휴 큐에서 그 응답을 들고 있는 컴포넌트를 찾아, 참조·파생 매칭 모두 못 찾으면 `unused` 로 둡니다(`inspect/unused.ts`). 반복 분류와 따로 붙는 표시입니다.

- 찾는 방법은 요청 상세의 "이 요청의 데이터를 쓰는 컴포넌트"(`findConsumers`)와 같습니다. 같은 요청(메서드·URL·payload)의 이전 응답 객체를 들고 있어도 쓰는 것으로 봅니다(structural sharing 은 같은 응답이면 이전 객체를 남깁니다). 트리 전체를 참조로 먼저 훑고, 참조로 못 찾은 요청만 파생으로 다시 훑습니다. 파생은 가장 잘 맞는 출처 하나가 아니라 기준(드문 값 2개 이상, 또는 원시값 필드 묶음과 값이 모두 같음)을 넘는 출처 모두를 봅니다. 다른 응답과 더 많이 겹쳐도 이 요청에서 왔을 수 있기 때문입니다. 다른 요청의 객체를 아무리 많이 들고 있어도 찾는 수 상한으로 멈추지 않습니다. 요청 상세도 같은 함수(`inspect/holders.ts`)와 같은 순서로 찾아 배지와 어긋나지 않습니다. rdx 패널 아래(요청 기록을 props 로 들고 있음)는 내려가지 않습니다.
- 판정하지 않는 요청: 변경 요청(POST, PUT, PATCH, DELETE. 응답은 결과 확인용), 실패 응답, JSON 이 아니거나 빈 본문(`[]`, `{}`), 무시한 엔드포인트, 새로고침 전 기록. 요청마다 한 번만 판정하고 고정합니다.
- 렌더 기록에 응답 객체가 나타났는지로 판정하지 않는 것은, 렌더에 쓰지 않고 state 에만 둔 응답을 놓치기 때문입니다. fiber 의 값을 훑는 쪽이 넓습니다.
- 빨강이 아니라 노랑인 것은 effect·핸들러에서만 쓰거나 가공해 새 객체로 만든 데이터도 이렇게 보이기 때문입니다(6). 배지는 세지 않고, 보고서 summary 에 medium 으로 싣습니다.
- 함께 기다림이 끝난 요청은 트리 한 번(참조, 못 찾은 것만 파생 한 번 더)으로 함께 판정합니다. 응답 30건이 몰려도 요청마다 트리를 훑지 않습니다.
- 트리를 조각으로 훑는 사이 commit 이 있었으면 찾은 컴포넌트가 아직 붙어 있는지(루트까지 이어지고 그린 DOM 이 문서에 있음) 확인한 것만 쓰는 것으로 정하고, 나머지는 다시 훑습니다(지난 fiber 를 봤거나 새로 마운트된 쪽을 못 봤을 수 있음). 쉬지 않고 그리는 화면에서 끝없이 돌지 않게 3번까지만 하고, 3번 모두 commit 이 끼면 판정하지 않습니다. 흔들리는 트리로 `unused` 라고 하지 않기 위해서입니다.
- commit 으로 기억해 둔 React 루트만 훑습니다. 기억한 루트가 없으면 판정하지 않습니다. 문서 전체를 `querySelectorAll('*')` 로 찾는 것은 사용자 조회에만 남깁니다.

"같은 요청"은 **메서드 + URL 전체(쿼리 포함) + payload**가 같을 때입니다. `configure({ keyHeaders })` 로 정한 요청 헤더가 있으면 그 값도 같아야 합니다.

- 같은 엔드포인트라도 쿼리나 payload가 다르면 다른 요청입니다. 쿼리를 빼고 비교했을 때 파라미터만 다른 요청끼리 우연히 응답이 같아도 낭비로 잘못 잡혔습니다.
- 쿼리 파라미터는 순서만 다르면 같은 요청으로 봅니다.
- 값이 요청 시작 시각 ±2초의 epoch(ms·초)인 쿼리 파라미터(`?_t=1730700000000`, jQuery 의 `?_=…`)는 캐시를 피하려고 보내기 직전에 붙인 값으로 보고 판정에서 뺍니다. 그 (이름, 값) 짝만 빼고, 같은 이름의 다른 값은 남깁니다. 이름만으로는 빼지 않습니다(같은 이름의 진짜 파라미터가 있을 수 있음). 창을 좁게 잡아 폴링의 `since=<직전 조회 시각>` 처럼 주기만큼 앞선 시각은 조건으로 남습니다. 뺀 파라미터는 요청 상세의 Query 에 적습니다.
- payload는 문자열, `URLSearchParams`, `FormData`(파일은 이름과 크기)를 비교합니다. `Blob`이나 스트림처럼 바로 읽을 수 없는 본문은 **판정에서 뺍니다.** 확신 없이 낭비로 표시하지 않기 위해서입니다.
- 엔드포인트별 집계는 쿼리를 뺀 "메서드 경로"로 모읍니다. 상대 경로와 절대 경로는 같은 엔드포인트로 합치고, 경로 안의 ID 는 하나로 묶습니다. Server Action 은 함수, GraphQL 은 연산 이름을 괄호로 붙여 나눕니다(`POST /graphql (GetUser)`: 본문의 `operationName`, 없으면 `query` 의 첫 이름 있는 연산, GET 은 `?operationName=`, 배치는 이름들을 처음 나온 순서로 하나씩 묶고, 이름 없는 persisted query 는 해시 앞 8자, multipart 업로드는 `operations` 필드). GraphQL 로 보는 것은 GraphQL 문서 모양의 `query`·`extensions.persistedQuery` 가 있거나 경로에 `graphql` 이 있을 때뿐입니다(`POST /api/track` 의 `operationName` 만으로는 나누지 않음). 64KB 넘는 본문은 파싱하지 않고 원문에서 이름을 찾습니다(variables 안의 `operationName` 키가 잡힐 수 있음). 무시 목록도 이 단위이고, 지금 엔드포인트와 맞지 않는 옛 무시 키는 요청 탭 아래에 따로 보여 지울 수 있습니다. 보고서 비교는 한쪽만 연산별로 나뉘어 있으면 이름 규칙이 바뀌었다고 경고합니다.
- 실패 응답의 중복은 따로 표기합니다. 로컬 환경 탓인 문제와 코드 탓인 문제가 섞이지 않게 하기 위해서입니다.
- 변경 요청(POST, PUT, PATCH, DELETE)의 응답이 도착한 뒤 1초 안에 나간 조회는 그 요청 때문으로 보고 묶어 보여 줍니다. 그중 직전과 같은 응답을 받은 수도 셉니다.
- 재조회 원인은 유휴 큐에서 한 번 정하면 고정합니다. 렌더나 분류 중에는 계산하지 않습니다.

### 4.4 렌더를 어떻게 보는가

React DevTools와 같은 `__REACT_DEVTOOLS_GLOBAL_HOOK__`의 commit 이벤트로 컴포넌트별 렌더 횟수와 commit 시각을 셉니다.

- react-dom은 로드될 때 이 훅에 등록하므로 rdx의 렌더 감시 모듈을 **react-dom보다 먼저** 평가합니다. React DevTools 확장이 없으면 최소한의 훅을 직접 만듭니다.
- 순서가 틀리면 오류 없이 렌더 탭이 비고 앞선 요청이 빠지므로, 훅은 렌더 감시가 꺼져 있어도 받은 commit 을 셉니다. 진입 모듈을 평가하고(패널 없이 보고서만 쓰는 설정도) 또는 `<RdxDevtools>` 가 마운트되고 2초 뒤 유휴 큐에서, 앱이 그려졌는데 commit 이 0 건이거나 설치 전에 시작한 fetch·XHR(resource timing)이 있으면 콘솔에 한 번 고치는 방법(엔트리 맨 위, Next.js 는 `instrumentation-client.ts`)과 함께 알립니다(#75). 2초를 기다리는 것은 rdx 보다 먼저 나간 요청이 끝나야 resource 항목이 생기기 때문입니다. 앱이 아직 그려지지 않았으면 몇 번 더 보고, 문제마다 한 번만 경고합니다. 주기 업로드는 commit 수가 바뀐 것만으로는 다시 보내지 않습니다(패널 자신의 commit 에도 늘어서).
- 부모가 bailout하면 자식 fiber는 지난 commit의 객체와 플래그가 그대로 남습니다. 같은 fiber 객체면 렌더하지 않은 것으로 봅니다.
- 렌더 감시는 RDX 버튼이 붙어 있는 동안 켭니다. 패널을 닫아도 버튼이 렌더 폭주를 알려야 하기 때문입니다. commit 훅의 비용은 프로젝트 목록 화면에서 8초에 58ms 정도였습니다.
- rdx 패널 자신의 렌더는 셈에서 뺍니다. 다만 패널의 메인 스레드 시간은 앱과 공유하므로, 렌더 탭은 요약을 유휴 큐에서 캐시해 계산하고 보이지 않을 때(패널 접힘, 다른 탭, 요청 상세가 덮을 때) 멈춥니다. 패널을 열어 둔 채 잰 체감 시간에는 rdx 몫이 섞일 수 있습니다.

### 4.4.1 렌더를 어떻게 줄일 수 있는지 보여 주는가

dev 환경이라 fiber에서 렌더 시점, 렌더 여부, 렌더 시간, 렌더 이유를 모두 알 수 있습니다. 횟수만 보여 주면 "그래서 무엇을 고치나"에 답하지 못하므로, 렌더마다 이전 fiber(alternate)와 비교해 이유를 나눕니다.

**렌더 여부.** React DevTools처럼 이번 commit에서 다시 만든 하위 트리(`fiber.child !== alternate.child`)만 내려가며 `PerformedWork` 플래그를 봅니다. 재사용된 하위 트리에는 지난 렌더의 플래그가 남아 있어 들어가면 오탐이 납니다. 예전에는 "같은 fiber 객체면 렌더 안 함"으로 봤는데, React가 fiber 객체를 재사용하는 경우(형제가 번갈아 업데이트) 렌더 11회 중 1회만 세는 문제가 감사에서 나와 바꿨습니다.

| 이유 | 판정 | 줄일 수 있나 |
|---|---|---|
| mount | 이전 fiber 없음 | 아니요 |
| state | `useState`·`useReducer`·`useSyncExternalStore`(queue가 있는 훅), 클래스 state, `useDeferredValue` 같은 값 훅이 바뀜 | 아니요 |
| context | 읽고 있는 context(`fiber.dependencies`) 값이 바뀜 | `React.memo`로는 안 됨. context 나누기, value `useMemo` |
| props | props 일부가 내용까지 바뀜 | 아니요 |
| 같은 내용 새 참조 | 바뀐 props가 참조만 다르고 내용은 같음(평범한 객체·배열만 JSON 비교, `children`은 빼고 판정) | 예. 부모에서 `useMemo`, 응답을 구조적 공유로 받기 |
| 새 콜백 | 바뀐 props 중 함수가 있고, 나머지는 내용이 같음 | 예. 부모에서 `useCallback` |
| 부모 렌더 | props·state·context가 그대로인데 부모가 렌더돼서 같이 렌더됨 | 예. `React.memo`(이미 memo인 컴포넌트는 세지 않음) |

렌더 시간은 React dev 빌드가 기록하는 `selfBaseDuration`(자식을 뺀 자기 자신의 렌더 시간)을 씁니다. 렌더 › 분석 탭은 기본으로 "줄일 수 있는 렌더"가 많은 순으로 정렬하고, 컴포넌트마다 이유별 횟수와 고치는 방법을 보여 줍니다. 전체 표시 박스 라벨에도 `↻N(불필요 M)`을 적습니다.

### 4.4.2 렌더와 네트워크를 어떻게 잇는가

렌더는 네트워크와 관계없이 일어날 수도 있습니다. 그래서 둘을 근거가 있을 때만 잇고, **네트워크와 무관한 비효율 렌더도 똑같이 보여 줍니다.**

- **렌더 → 네트워크.** 렌더마다 원인을 붙입니다.
  - 직접: 새로 바뀐 state·props·context 안에 응답 객체가 있고, 그 응답이 렌더 직전 3초 안에 도착함. 시간 조건은 예전 응답 데이터를 담은 채 다른 이유로 state를 바꾼 경우(`setState({...prev, filter})`)를 걸러 내기 위한 것입니다.
  - 부모를 따라: 같은 commit에서 네트워크 응답 때문에 렌더된 가장 가까운 조상을 따라 렌더됨. 자기 state가 바뀐 렌더는 조상을 이어받지 않습니다.
  - 렌더 › 분석 탭에 "네트워크 응답으로 N회 · 네트워크와 무관 M회"를 나란히 보여 주고, 원인 요청을 누르면 요청 상세가 열립니다.
- **엔드포인트별 렌더 비용.** 렌더마다 붙인 원인 요청을 엔드포인트(`endpointOf`)별로 모아, 그 응답이 일으킨 렌더 수·자기 렌더 시간 합과 그중 같은 응답(직전과 똑같은 본문)으로 일어난 것을 네트워크 탭의 엔드포인트 행과 보고서 `requests.endpoints[].renders` 에 보여 줍니다. 같은 응답으로 일어난 렌더는 재요청을 없애면 그대로 사라지는 낭비라, summary 의 추정 절감(`savings.renders`·`renderMs`)에도 씁니다.
  - 직접 렌더와 부모를 따라 렌더된 자손을 **모두** 셉니다. 응답 하나가 화면에 일으킨 일의 크기는 자손까지 합쳐야 맞고, 재요청을 없애면 자손 렌더도 함께 사라지기 때문입니다. 다만 고칠 곳이 다르므로(받은 컴포넌트의 setState, 자손의 memo) 부모를 따라 렌더된 몫을 `viaParent` 로 나눠 둡니다. 직접만 세는 것과 나누지 않고 합만 보이는 것은 각각 비용을 작게 보이거나 고칠 곳을 가려서 하지 않았습니다.
  - 렌더 기록은 이미 유휴 큐에서 만든 것이라, 집계는 기록을 세기만 합니다. 네트워크 탭은 엔드포인트별 보기를 띄운 동안에만 1초마다 유휴 큐에서 조각으로 세고(요청 상세가 덮으면 쉽니다), 보고서는 만들 때 셉니다. 한 컴포넌트의 기록은 한 조각 안에서 끝까지 봅니다. 쉬는 동안 commit 이 기록을 밀어내거나 reset 이 비우면 같은 렌더를 두 번 세기 때문입니다. 구간과 인스턴스 상한(5000)은 렌더 탭·보고서의 렌더 그룹과 같고, 보이는 요청(경로 필터, 기록 상한 안)이 원인인 렌더만 셉니다. 렌더 감시는 RDX 버튼이 붙어 있는 동안 켜 두므로(4.4) 네트워크 탭이 따로 켜지 않습니다.
  - 시간은 dev 빌드의 `selfBaseDuration` 합이라 production 보다 큽니다. 절대 시간이 아니라 엔드포인트끼리, 고치기 전후로 견주는 값입니다.
- **요청 → 요청(워터폴).** 응답 A 가 원인인 commit(렌더 원인 `cause.record`)에서 컴포넌트 X 가 마운트됐고, X 가 그 commit 의 effect 에서(요청의 commit 순번이 그 commit, `useLayoutEffect` 면 앞 순번) 2초 안에 요청 B 를 보냈으면 A → B 로 잇습니다(#86). 마운트 렌더의 원인 요청은 monitor 가 commit 기록(`commitCauses.ts`)에 적고, B 의 판정은 유휴 큐에서 요청을 만든 직후에 고정합니다(이름마다 최근 commit 만 남아서). commit 순번이 같으면 요청이 commit 시각 뒤(useEffect), 다음 순번이면 commit 시각 앞(useLayoutEffect)이어야 하고, 이 마운트 판정은 StrictMode 판정과 같은 함수(`repeatCause.ts` 의 `mountAt`)를 씁니다. A 의 응답 전에 시작한 요청(같은 때 병렬로 나간 요청)은 잇지 않습니다. 마운트 원인은 응답 객체로 확인한 것(direct, 그리고 direct 원인인 조상을 따른 렌더)만 씁니다. 응답 직후의 state 변경을 시간으로만 짐작한 timing 원인과 그것을 이어받은 렌더는, 우연히 응답 직후 다른 이유로 마운트된 컴포넌트를 고리로 잘못 잇기 쉬워 뺐습니다. StrictMode 가 effect 를 다시 돌려 같은 요청이 둘 나가면 둘 다 잇되, 고리를 셀 때는 취소되지 않은 쪽(대개 재실행) 하나만 봅니다. 고리를 이어 깊이(요청 수)와 늘어난 지연(응답 시간 합)을 보고서 `requests.waterfalls` 와 타임라인 화살표로 보여 줍니다. B 가 A 의 데이터를 실제로 쓰는지는 판정하지 않고, 처방에서 두 경우(병렬화·prefetch / 서버에서 합치기·route loader)를 나눕니다.
- **네트워크 → 컴포넌트.** 요청이 보이는 곳(요청 목록, 타임라인 막대, 렌더 탭의 원인 요청 등)에 호버하면, 그 요청의 응답 객체를 props·훅 state로 들고 있는 컴포넌트를 화면에서 주황 점선으로 강조합니다. 요청 상세에는 "이 요청의 데이터를 쓰는 컴포넌트" 목록이 나옵니다. React Query는 응답이 같으면 이전 객체를 재사용하므로, 같은 요청(메서드·URL·payload)의 이전 응답까지 함께 찾습니다.

### 4.4.3 응답 때문에 화면이 밀렸는가: 레이아웃 이동

렌더 횟수는 개발자가 보는 비용이고, 사용자가 느끼는 것은 로딩 표시가 콘텐츠로 바뀌며 화면이 밀리는 것입니다. 브라우저는 밀린 DOM 노드만 알려 주고 어느 응답·컴포넌트 때문인지는 모릅니다. rdx 는 DOM → fiber 와 그 commit 의 네트워크 원인을 이미 알고 있어 둘을 잇습니다(#89).

- 가로채기와 함께 `PerformanceObserver({ type: 'layout-shift', buffered: true })` 를 설치합니다(`core/render/layoutShifts.ts`). `buffered` 라 rdx 를 불러오기 전(첫 그리기)의 이동도 받습니다. 콜백에서는 항목 참조만 담고, 노드 → fiber 잇기는 유휴 큐에서 합니다.
- 사용자 입력 직후 500ms 안의 이동(`hadRecentInput`)은 브라우저도 CLS 에서 빼므로 같이 뺍니다. 밀린 노드가 모두 rdx 패널 것이면 기록하지 않습니다.
- 이동 시각은 콜백에서 `Date.now() - (performance.now() - startTime)` 으로 렌더 기록과 같은 `Date.now` 시계로 바꿉니다. `timeOrigin + startTime` 은 시스템 시간 조정·잠자기 뒤 `Date.now` 와 어긋날 수 있기 때문입니다.
- 밀린 노드(`sources[].node`, 글자 노드면 그 요소)에서 가장 가까운 앱 컴포넌트를 찾습니다. 그 컴포넌트와 조상의 렌더 가운데 이동 시각 이전 1초 안의 가장 늦은 commit 을 고르고(이전 렌더가 없을 때만 이동 뒤 한 프레임(16ms) 안의 렌더), 그 commit 에서 아래부터 처음 만난 네트워크 원인(4.4.2)을 원인 요청으로 씁니다. 이전 렌더가 있으면 뒤의 렌더는 고르지 않습니다(다음 commit 이 원인을 가로채지 않게). 부모를 따라 렌더됐으면 같은 응답을 직접 받은 조상을 원인 컴포넌트로 올립니다(자리를 예약할 곳은 대개 그 컴포넌트입니다). 밀린 노드가 여럿이면 원인 요청을 찾은 첫 노드를 씁니다.
- 밀린 컴포넌트와 조상에서 원인을 못 찾으면(위쪽 형제가 응답을 받아 커져 아래가 밀림) 같은 시간 규칙으로 고른, 응답으로 렌더된 가장 가까운 commit(어느 컴포넌트든)의 원인을 `inferred: true` 로 둡니다. 보고서는 그대로 싣고 타임라인은 흐린 표시와 "likely" 로 보여 줍니다. 확실하지 않으므로 처방 전에 코드로 확인해야 합니다.
- 원인은 렌더 기록으로 찾으므로 이동이 일어날 때 렌더 감시가 꺼져 있었으면(패널 없이 보고서만 쓰는 설정, RDX 버튼이 붙기 전 첫 로딩) 컴포넌트만 남기고 `causeUnavailable: 'render-monitoring-off'` 를 붙입니다. howToRead 가 `reset()`(감시를 켬) 뒤 다시 재라고 안내합니다.
- 이동 기록은 요청 기록을 들지 않고 요청 id 와 엔드포인트만 둡니다. 타임라인에서 누르면 지금 목록에서 id 로 찾고, 밀려났으면 "Request no longer in the list" 를 보여 줍니다.
- 보고서 `layoutShifts[]`(점수 큰 순 20개, 값·밀린 컴포넌트와 위치·원인 엔드포인트와 컴포넌트). `summary` 는 20개로 자르기 전 이동 전부를, 같은 컴포넌트·위치·원인 요청끼리 묶어 점수 합이 0.1(web-vitals 의 CLS "좋음" 상한) 이상이면 `layout-shift` finding(medium)으로 올립니다. 컴포넌트도 원인도 모르는 이동은 고칠 곳이 없어 올리지 않고, verdict 는 밀린 컴포넌트(이름·위치)를 한 번씩만 셉니다. 처방은 자리 예약(최종 크기의 skeleton, `min-height`, 이미지 `width`·`height`)입니다. 타임라인에는 렌더 영역 위에서 점수만큼 내려오는 분홍 표시로 그리고, 누르면 원인 요청 상세가 열립니다.
- 측정 시작(`reset()`) 전의 이동은 버리고, 최근 200건만 둡니다.
- layout-shift 항목은 Chromium 계열(Chrome, Edge)만 줍니다. Safari·Firefox 에서는 오류 없이 꺼지고 보고서에 `layoutShifts` 가 없으며 타임라인 범례에도 나오지 않습니다.
- 로딩 표시가 아주 짧게 나타났다 사라지는 깜빡임은 레이아웃 이동이 아니라 따로 검토합니다.

### 4.5 요청 상세를 어떻게 보여 주는가

dev 환경 전용이라 요청과 응답의 원문을 보관해도 됩니다. 요청 헤더(`fetch`의 `init.headers`, XHR의 `setRequestHeader`), 응답 헤더, 응답 원문(텍스트 계열만, 요청당 최대 100KB)을 남깁니다. SSE, ndjson 같은 스트리밍 응답은 끝까지 버퍼링하지 않도록 원문을 읽지 않습니다. 실패, 취소, 타임아웃된 요청도 에러와 함께 기록합니다.

### 4.6 출처를 필드까지, context 까지

- **필드 수준.** 요소를 누르면, 가장 가까운 컴포넌트의 출처를 누른 글자와 값이 같은 필드(`$.data.summary.total`)로 좁힙니다. 같은 값이 그 안에 하나뿐일 때만 좁히고(0 처럼 흔한 값은 그대로), 숫자는 천 단위 쉼표를 걷어 비교합니다.
- **context.** 컴포넌트가 읽는 context 값(`fiber.dependencies`)도 출처를 찾습니다. 다만 그 값과 바로 아래 한 단계까지만 봅니다. 라우터 상태처럼 응답을 깊이 품은 context 를 읽기만 하는 래퍼(NavLink 등)를 소비자로 잡지 않으려는 것입니다. 요소 검사에서는 props·훅에서 못 찾았을 때만 context 를 씁니다.
- **복사본.** 응답을 펼쳐 복사하고 필드를 덧붙인 객체(`{...json, before}`)는 값이 작은 숫자뿐이면 "드문 값 2개 이상" 기준을 못 넘습니다. 원시값 필드 이름 묶음(3개 이상)과 값이 모두 같으면 같은 데이터로 봅니다.
- **과다 응답(하한값).** 요청 상세의 "Fields visible on screen (lower bound)" 에 "Visible fields 12 / 180 · 400 KB" 처럼, 응답의 leaf 필드 중 값이 그 응답을 쓰는 컴포넌트(위의 소비자)의 **보이는** 글자에 나타난 수와 응답 원문의 UTF-8 바이트를 보여 줍니다(XHR `responseType: 'json'` 은 객체를 다시 직렬화해 세므로 `≈`). 비교 규칙은 필드 좁히기와 같고(글자 노드 하나와 값이 같음, 숫자는 천 단위 쉼표를 걷음), 200자보다 긴 글자도 2000자까지는 통째로 그렸으면 셉니다. 비교하지 않는 값은 갈래별로 따로 셉니다: 흔한 값(0·true·한 글자, 파생 매칭과 같은 기준), 2000자를 넘는 글자, null·빈 글자. `script`·`style`·`template`·`noscript`, `hidden`·`display:none`·`visibility:hidden`(`checkVisibility`) 안의 글자와 rdx 자신의 UI 는 읽지 않습니다(aria-hidden 은 보이므로 읽습니다). 보이지 않게 쓰는 필드(id, 정렬 키, 조건)는 셀 수 없으므로 **하한값**이고, 값이 같은 다른 필드나 고정 문구와 우연히 같은 값도 보인 것으로 셉니다. 상세를 열 때, 연 채로 기록이 바뀌어 소비자를 다시 찾았을 때(1초 조용해진 뒤, 큐는 비우지 않음), 소비자 DOM 이 바뀌었을 때(0.5초 조용해진 뒤) 다시 셉니다. 셀 때도 큐를 그 자리에서 비우지 않고 유휴 큐에서 조각(500 노드씩, 배열·객체의 자식은 하나씩 꺼내 10만 개 배열도 한 조각에 500개까지만)으로 셉니다. 글자를 모으는 조각 사이에 앱이 다시 그려 지나던 노드가 문서에서 빠지면 처음부터 다시 모아 수가 조용히 줄지 않게 합니다(#88).
  - **Proxy 로 읽는 필드를 추적하지 않습니다.** 응답을 Proxy 로 감싸면 참조 동일성이 깨져 rdx 의 객체 참조 추적(4.2)과 React Query 의 structural sharing 이 망가지고, `JSON.stringify`·`replaceEqualDeep` 가 모든 키를 읽어 결국 전부 "읽힘" 이 됩니다. 앱이 속성을 읽을 때마다 비용이 들어 앱 경로 원칙(4.10)에도 어긋납니다.
  - **보고서에는 넣지 않습니다.** 응답마다 소비자를 찾으려면 fiber 트리 전체를 훑고 DOM 글자를 읽어야 하는데, 보고서는 플러그인이 5초마다 만들므로 싸지 않습니다. 요청 상세에서만 보여 줍니다.

### 4.7 렌더를 시작한 조상

"부모를 따라 렌더"만 보여 주면 어디를 고칠지 모릅니다. commit 을 위에서 아래로 내려가며, 스스로 렌더를 시작한 컴포넌트(state·context 변경, mount)를 자손에게 물려줍니다. props 변경이나 부모를 따라 렌더된 자손은 그 조상을 이어받습니다. 렌더 탭과 보고서에 "렌더 시작: <ProjectList>(state) 24회" 로 보이고, 고칠 곳은 대개 이 조상의 setState 입니다. 같은 응답(직전과 똑같은 본문)으로 일어난 렌더는 따로 셉니다. 그리는 JSX 위치는 dev 빌드의 `_debugSource` 로 붙입니다(React 19 처럼 없으면 생략).

### 4.8 React Query 캐시키 점검

react-query 를 import 하지 않고, fiber 에서 `QueryClientProvider` 의 `client` 를 객체 모양으로 찾습니다. QueryCache 를 구독해 쿼리 함수가 실제로 가져온 성공만 기록합니다(`setQueryData`·`initialData` 는 요청이 아닙니다). 이벤트에서는 데이터(WeakRef)와 시각만 남기고 출처 매칭은 점검할 때 해서, 앱의 dispatch 안에서 일을 늘리지 않습니다.

- 같은 요청을 다른 키로 캐시(duplicate-cache), 같은 키로 다른 요청(key-missing-param), 이 화면에서 만든 적 없는 키의 무효화(invalidate-miss, react-query 의 partialMatchKey 와 같은 규칙), staleTime 0 인데 같은 응답 재요청(stale-zero, refetchInterval 폴링 제외)
- 무효화 키의 모양은 본 적 있지만 그 값의 쿼리만 아직 없으면 invalidate-unloaded 로 나눠 회색 한 줄로 묶습니다. 실제 앱의 권한 저장에서 상속 범위 무효화가 invalidate-miss 오탐으로 107건 나왔기 때문입니다.
- 짧은 시간 안에 같은 쿼리를 덮는 무효화를 두 번 부르면 double-invalidate 로 짚습니다. 뒤 무효화가 앞의 재조회를 취소해 같은 요청이 두 번 나갑니다.
- 요청 상세에는 React Query 요청이 왜 나갔는지(관찰자, fetch 원인)를 보여 줍니다.
- structural sharing 이 데이터를 복사하면 필드 값으로 찾되, 성공 직전 5초 안에 끝난 요청만 씁니다. 기록은 2분 뒤 버립니다.

### 4.9 AI 에게 결과 넘기기와 탭 단위 유지

- **보고서.** `window.__RDX__.report()` 와, dev 서버 플러그인(`react-data-xray/vite`, `react-data-xray/middleware`, Next.js route `react-data-xray/next`)이 5초마다 쓰는 `.rdx/report.json`. 응답 본문과 헤더는 넣지 않습니다. `reset()` 으로 측정을 새로 시작하고 `snapshot(이름)` 으로 `.rdx/<이름>.json` 을 따로 남깁니다. 보고서에는 마지막 reset 시각(`resetAt`)이 남습니다. 5초 주기 파일은 유휴 큐를 비우지도, 소스맵을 기다리지도, queryKey 문맥을 찾지도 않으므로(주기 작업은 그때까지 분석된 것만), 보고서에 `complete`·`incompleteReasons` 로 그 사실을 드러내고 비교에는 snapshot 을 쓰게 합니다. 남은 분석은 보고서에 들어가는 일만 셉니다(`enqueue(step, 'ui')` 로 넣은 오버레이·렌더 탭 일은 세지 않습니다). snapshot 도 소스맵은 2초까지만 기다리므로 늘 끝난다고 약속하지 않고, 못 끝나면 `source-map-timeout` 으로 알립니다. 보고서 맨 앞의 `summary` 는 이미 만든 섹션으로 고칠 것의 순위만 매기고(새 분석 없음), severity 는 RDX 버튼 배지와 같은 기준(`core/problems.ts`)을 써서 둘이 다른 말을 하지 않게 합니다. `howToRead` 는 `howToReadVersion` 으로 판을 남기고 `report({ howToRead: false })` 로 뺄 수 있습니다. 파일로 남기는 보고서에는 늘 싣습니다.
- **탭별 보고서.** 탭마다 보고서를 따로 저장하고 열린 탭 목록을 둡니다. 여러 탭을 열어 둔 채 재도 결과가 서로 덮이지 않게 하기 위해서입니다.
- **전후 비교.** `compare(전, 후)` 와 패널의 Compare 는 이 탭에서 저장한 두 보고서의 증감을 보여 주고 `.rdx/compare-<전>-<후>.json` 에도 남깁니다. 스냅샷은 최근 6개까지 탭에 둡니다. 측정 구간이나 화면(`page`)이 다르거나, 한쪽만 reset 뒤에 쟀거나, 한쪽에서 렌더 감시가 꺼져 있었거나 렌더 인스턴스 상한에 걸렸으면(`truncated`) 증감을 믿기 어려우므로 경고합니다. 행마다 `verdict` 를 둡니다. 양쪽에 있는 행은 improved·regressed·unchanged(낭비 먼저, 그다음 전체 수)이고, 한쪽에만 있는 행은 0 과 견주지 않고 new·gone 입니다(낭비가 있는 새 행만 regressed, 낭비가 있던 사라진 행만 improved). 요청 수·낭비 요청·렌더·줄일 수 있는 렌더에는 `totals` 를 두고, 기록 상한으로 요청을 버린 쪽이 있으면 요청 합계는 unknown 입니다. 보고서의 렌더 행은 30개까지라 고친 뒤 순위가 밀린 컴포넌트가 사라진 것(가짜 개선)처럼 보일 수 있어, snapshot 이 저장할 때만(`buildSnapshotReport`, 주기 업로드는 하지 않음) 상한 밖 행을 200개까지 더 만들어 비교용 부분에 담고(스냅샷 하나에 수십 KB 이하), 보고서는 상한 밖 행의 수와 합(`renders.omitted`)과 fetch 원인 상한 밖 묶음 수(`reactQuery.fetchCausesOmitted`)만 싣습니다. 그래도 한쪽에서 상한 밖에 있었을 수 있는 행(파일에서 읽은 보고서, 옛 스냅샷, fetch 원인 20개 상한)은 removed 가 아니라 `unknown` 으로 보입니다. 플러그인이 없는 dev 서버에서는 파일 없이 탭에만 남깁니다.
- **보내기 전 확인.** 플러그인이 없는 dev 서버는 `/__rdx/report` 를 원격 백엔드로 프록시할 수 있습니다(whatap-front 가 그렇습니다). 그래서 본문 없는 GET 으로 미들웨어 표시 헤더를 확인한 뒤에만 보냅니다. 미들웨어는 Host 를 로컬 이름·IP·`allowedHosts` 로 제한하고(DNS 리바인딩), Origin 을 포트까지 비교하며, 임시 파일에 쓴 뒤 이름을 바꿉니다.
- **원본 위치.** 호출 스택의 http 프레임을 모듈의 `sourceMappingURL` 로 원본 위치(`src/api/client.ts:42`)로 바꿉니다. 세 모델 감사에서 "줄 번호가 원본과 다르다"가 공통 지적이었습니다.
  React Query finding 의 무효화 호출 위치(`stack`·`stacks`)도 같은 길로 바꾸고, 앱 프레임 앞쪽 3줄로 자릅니다. 변환은 요청 callers 와 같은 진행 중 목록에 넣어 보고서 저장 전 소스맵 대기가 함께 기다립니다. `causedBy`·`heaviestCommits[].startedBy` 에는 렌더를 시작한 컴포넌트의 JSX 위치(`renderedAt`)를 붙여, 같은 이름의 조상이 여러 곳에 있어도 고칠 곳을 특정합니다(#73). 위치는 렌더 기록마다 둔 작은 행 칸(`ComponentSite`: 이름·위치·패키지·그린 앱 컴포넌트)에서 보고서를 만들 때 읽습니다. 소스맵이 풀리면 이 칸도 고쳐 바뀐 줄이 따라오고, 렌더 원인·commit 은 렌더 기록(fiber·이벤트) 대신 이 칸만 듭니다. 조상은 이 칸으로 만든 행 id 로 세어, 같은 자리의 여러 인스턴스가 한 칸에 듭니다. React Query finding 은 기록한 그대로의 위치를 묶기 키로 두고 원본 위치는 따로(`resolvedStack`) 두어, 같은 호출 위치가 변환 전·후로 갈리지 않습니다.
- **섹션 공통 id(#73).** 엔드포인트는 `ep:<endpoint>`, 컴포넌트는 `c:<이름>@<renderedAt>`(위치를 모르면 `c:<이름>`)로 섹션·summary·compare 가 같은 대상을 가리킵니다. 숫자 id 는 실행마다 달라져 compare 에 쓸 수 없어 이름 + 위치로 만듭니다. 라이브러리 행은 렌더 그룹 키와 같이 `c:<이름>(<패키지>)<<그린 앱 컴포넌트>@<위치>` 로 갈라 id 가 겹치지 않습니다. 요청을 보낸 컴포넌트는 스택에서 이름만 알아 `c:<이름>` 이고, 렌더 행과는 접두어로 맞춥니다. 소스맵이 늦게 풀리면 위치가 바뀌어 id 도 바뀌므로, 비교는 `complete: true` 인 snapshot 으로 합니다.
- **자가 점검.** `window.__RDX__.doctor()`, 패널 도구 막대의 Status, 보고서의 `diagnostics` 가 같은 값입니다: commit 수·React 버전·StrictMode, 가로채기 설치와 설치 전 요청 수, 기록한 요청과 출처를 등록한 JSON 응답 수, 보고서 플러그인 상태, 소스맵 실패 수, 같은 응답 판정 메모리, 찾은 문제와 고치는 방법. 이미 있는 카운터와 import 순서 판정 결과만 읽고 큐를 비우지 않습니다(resource timing·DOM 을 다시 훑지 않고, StrictMode 는 기록한 앱 렌더의 fiber 모드 비트로 봅니다). 도구 막대 버튼의 문제 수는 렌더마다 싼 값만 셉니다. 빈 상태 문구(연결된 응답 없음, 렌더 없음)도 이 값으로 이유를 붙입니다. 문구는 `core/diagnostics/messages.ts` 한곳에 두어 언어 선택(#45) 때 바꿉니다(#76).
- **브라우저 없이 부르기(#69).** 브라우저 도구가 없는 에이전트도 reset → 시나리오 → snapshot → compare 를 혼자 돌리도록 `react-data-xray` CLI(`reset`·`snapshot`·`compare`·`report`·`tabs`, 앱 안에서는 별칭 `rdx`)와 같은 도구를 내는 stdio MCP 서버(`react-data-xray mcp`)를 둡니다. 주 실행 파일 이름을 패키지 이름으로 둔 것은 npm 의 `rdx` 가 다른 패키지라 앱 폴더 밖의 `npx rdx` 가 그것을 받아 실행하기 때문입니다. CLI 가 `POST /__rdx/command` 로 명령을 맡기면 dev 서버가 탭별로 메모리에 두고(받아 가지 않으면 CLI 의 `--timeout` + 10초 뒤 버림. 받아 간 명령은 그 탭이 계속 알리는 동안 버리지 않음), 탭은 업로드·받아 가기의 응답으로 받아 `window.__RDX__` 의 reset·snapshot 을 그대로 부른 뒤 `POST /__rdx/report?command=<id>` 로 결과를 알립니다. CLI 는 `GET /__rdx/command/<id>` 로 기다립니다.
  - 받는 쪽은 업로드 주기를 그대로 씁니다. 보고서가 그대로라 올리지 않는 주기에는 본문 없는 `GET /__rdx/report?tab=` 로 받아 가며, 명령이 없으면 204 라 아무것도 읽지 않습니다. CLI·MCP 를 쓰지 않을 때는 55초에 한 번만 받아 가고, 명령 경로에 요청이 오면 dev 서버가 10분 동안 응답에 `x-rdx-cli` 를 붙여 5초마다 받아 가게 합니다. 쓰지 않는 사용자의 dev 서버로 5초마다 요청이 나가지 않게 하려는 것이고, 대신 첫 명령은 최대 1분 늦습니다. 앱 경로 비용은 없습니다. Vite 의 `server.ws` 로 바로 보내는 안은 webpack·Next 에 없는 길이라 두지 않았고, 오래 걸어 두는 요청(long-poll)은 HTTP/1 의 호스트당 연결 6개 중 하나를 계속 차지해 뺐습니다. 오래 가려진 탭은 브라우저가 타이머를 1분에 한 번으로 늦추므로, 받아 가기 주기를 1분보다 짧게(55초, 보낸 때부터 셈) 두어 깰 때마다 받아 가게 하고, 연결된 탭 판정은 130초, CLI 대기 기본값은 90초입니다. 업로드가 연달아 실패하면(dev 서버 재시작) 멈추지 않고 올리기만 쉬며 받아 가기를 이어 가다가 되면 다시 올립니다.
  - 시간 제한: 명령은 CLI 의 `--timeout` 이 되는 순간 버립니다(받아 가지 않았으면 실행하지 않음, 받아 갔으면 "실행됐을 수 있음"). CLI 는 시간 초과·Ctrl+C 때, MCP 는 클라이언트가 취소할 때 `DELETE /__rdx/command/<id>` 로 거두고, 탭은 실행 직전에 아직 살아 있는지 물어(`GET /__rdx/report?command=`) 앞 명령을 기다리는 사이 포기된 명령을 실행하지 않습니다. 결과 알림은 실패하면 간격을 늘려 몇 번 더 보내고, 끝난 명령에 늦게 온 결과는 받지 않습니다.
  - 탭이 받아 가는 길을 보고서 경로에 둔 것은 Next 가 route 파일마다 따로 붙기 때문입니다. 명령 route 를 두지 않은 앱도 탭은 404 페이지를 5초마다 그리지 않습니다. CLI 쪽만 `app/%5F_rdx/command/[[...id]]/route.ts`(GET·POST·DELETE)가 필요하고, Next dev 는 route 마다 모듈을 따로 평가하므로 큐는 `globalThis` 에 둡니다. 보고서 경로를 바꾸면(`configure({ reportPath })`, 서버의 `path`, #78) 탭은 그 경로로 받아 가고, 명령 경로는 같은 밑으로 옮깁니다(`/x/report` → `/x/command`, 그 밖은 `<path>/command`). dev 서버가 그 경로를 `.server.json` 의 `commandPath` 에 적어 두면 CLI 가 따릅니다.
  - 탭을 고르지 않으면 보이는 탭(`visibilityState`) 중 최근 2분 안에 포커스를 받은 탭에서 실행하고 다른 탭을 알립니다. 탭이 하나뿐이면 그 탭입니다. 보이는 탭이 여럿인데 최근에 포커스를 받은 탭이 없으면 짐작하지 않고 목록과 함께 `--tab` 을 묻습니다(종료 코드 6). 엉뚱한 탭을 reset 하면 측정이 조용히 틀어지기 때문입니다. 포커스 시각은 시계가 다른 기기도 있어 "몇 ms 전"으로 받습니다.
  - 보안: 보고서 경로와 같은 Host·Origin·content-type 검사에 더해, 명령 경로의 모든 요청(만들기·상태·탭 목록)에 dev 서버가 처음 요청을 받을 때 만든 무작위 토큰(`x-rdx-token`)이 있어야 합니다. 토큰은 `.rdx/.server.json`(0600)에만 있어 같은 PC 에서 그 파일을 읽는 도구만 보낼 수 있습니다. 명령을 주고받는 쪽(명령 경로, 탭 등록·받아 가기·결과)은 소켓 주소가 루프백인 요청만 받습니다. Host 는 보내는 쪽이 꾸밀 수 있어 소켓 주소로 보고, 소켓이 없는 Next 만 Host 이름으로 봅니다. 그래서 `vite --host` 로 연 LAN 의 기기는 토큰이 없어 명령을 보내지 못하고, 탭인 척 등록해 명령을 가로채지도 못합니다. 다른 기기의 탭을 쓰려면 `commands: 'lan'` 으로 켭니다(그러면 같은 망의 기기가 가짜 탭으로 명령을 받아 갈 수 있음을 문서에 적었습니다). 페이지마다 비밀값(pageKey)을 주는 안도 봤지만, 일반 HTTP 클라이언트도 같은 핸드셰이크로 받아 갈 수 있어 루프백 제한보다 나을 것이 없어 두지 않았습니다. 브라우저 쪽은 토큰이 필요 없습니다. 탭 등록·받아 가기 GET 은 `x-rdx-tab` 헤더가 있어야 합니다. 다른 사이트는 이 헤더를 붙이려면 preflight 가 필요해 보내지 못하고, 헤더 없는 GET(`<img>` 등)은 아무것도 바꾸지 않는 핸드셰이크로 답합니다. 페이지가 정한 제목·경로는 믿을 수 없는 값이라 CLI·MCP 가 제어 문자를 지우고 잘라 "page title" 로 따옴표에 넣어 보여 주고, 기억하는 탭 수에도 상한(50)을 둡니다. 명령은 측정 기록만 바꾸는 reset·snapshot 뿐이고 임의 코드는 실행하지 않습니다. 결과는 맡은 탭이 알린 것만 받습니다.
  - dev 서버 주소는 서버가 요청을 받은 소켓의 로컬 주소·포트로 만들어 `.rdx/.server.json` 에 적고 CLI 가 읽습니다(`.` 으로 시작해 snapshot 이름과 겹치지 않습니다). 처음에는 브라우저의 Origin 을 적었지만, LAN 의 기기가 자기 Host·Origin 으로 보내면 CLI 가 토큰을 그 기기로 보내게 되어 바꿨습니다. 소켓이 없는 Next 는 주소를 쓰지 않으므로(재시작 때 지난 주소는 지우지 않습니다) `--url` 이 필요합니다. CLI 는 명령 경로를 `--url` 의 경로 밑에 붙입니다(`--url http://localhost:3000/docs` → `/docs/__rdx/command`). Next 의 route 는 `basePath` 를 모르고 기본 명령 경로를 적으므로, basePath 를 쓰는 앱은 basePath 까지 넣은 `--url` 로 부릅니다. dev 서버가 적는 주소는 경로가 없어 그대로입니다. 파일은 내용이 바뀌었거나 지워졌을 때 다시 씁니다.
  - `react-data-xray compare` 는 `.rdx/<이름>.json` 파일만 읽어(이름은 snapshot 과 같은 규칙이라 폴더 밖을 가리킬 수 없습니다) `compare.ts` 로 비교합니다. 브라우저의 compare 는 그 탭 sessionStorage 의 스냅샷만 읽어 탭을 새로 열면 쓰지 못하던 것도 함께 풀립니다.
  - MCP 는 initialize·tools/list·tools/call·ping 만 직접 구현했습니다. CLI·MCP 는 사용자 개발 환경에서 돌므로 SDK 를 런타임 의존성으로 두면 모든 사용자에게 함께 설치됩니다.
- **AI 스킬.** `skills/rdx-perf/SKILL.md`: 측정 → 결과 읽기 → 원인 확인 → 처방 → 다시 측정의 순서와 지킬 것.
- **탭 단위 유지.** 패널 열림·박스·관점과 요청 기록을 sessionStorage 에 둡니다. 요청 기록은 페이지를 떠날 때 저장하고(응답 객체 제외, 원문 10KB·전체 500KB, 비밀번호·토큰 가림), 되살린 뒤 저장소를 비웁니다. 주기 판정은 페이지 로드별로 해서 새로고침 사이 간격이 주기를 깨지 않게 합니다.

### 4.10 측정 대상을 느리게 하지 않기

프로젝트 목록(카드 100개, 10초 폴링, 응답 최대 1MB)에서 처음에는 전체 표시가 메인 스레드를 109% 차지했습니다. 지금은 1% 안팎입니다.

- 박스 목록이 바뀔 때만 React 로 그리고, 위치·깜빡임·렌더 횟수·지표는 rAF 에서 DOM 에 직접 씁니다(위치는 모두 읽은 뒤 씁니다).
- 박스 수집은 commit 이 몰려도 1초에 한 번, 파생 조회는 수집당 4ms 로 끊고, props·값 객체 단위로 결과를 기억합니다.
- 쓰지 않는 응답 판정은 fiber 하나마다, fiber 안에서는 객체 32개·파생 후보마다 멈출 수 있게 트리를 스택으로 훑고, step 하나는 1ms 로 끊습니다(큰 목록을 든 fiber 하나도 조각을 넘지 않습니다). 4,000 fiber 화면(jsdom)에서 소비자가 없어 참조·파생을 끝까지 훑는 최악의 경우, 응답 1건은 유휴 시간 160~230ms·조각 27~33개, 함께 끝난 응답 30건(출처 등록·색인 포함)은 270~350ms·조각 36~38개였습니다. 가운데 조각은 4~7ms, GC 멈춤이 낀 몇 조각은 16~38ms 입니다(할당 없는 바쁜 루프만 돌려도 jsdom 에서는 8ms 조각이 나옵니다). 테스트는 가상 시계로 조각마다 시간을 보며 끊는지를 고정합니다. 요청마다 한 번이라 반복되지 않습니다.
- 파생 색인은 응답별 조각으로 나눠 새 응답만 유휴 큐에서 조금씩 색인하고, 목록에서 밀려난 응답은 바로 버립니다(힙 600MB → 300MB, GC 멈춤 제거). 조회는 드문 값 두 개의 후보만 비교합니다.

**앱 경로에서는 참조만 담습니다.** React commit, fetch/XHR, `res.json()`, `JSON.parse` 안에서는 참조만 담고, 분석은 유휴 큐(`src/core/scheduler/idleQueue.ts`)에서 한 번에 4ms 이하 조각으로 합니다. rdx 때문에 앱이 기다리면 재려는 값이 틀어지기 때문입니다.

- **밀려도 버리지 않습니다.** 앱이 계속 바쁘면 분석이 밀리지만, 상한을 넘은 분석을 버리고 세는 대신 전부 분석하고 끝나는 대로 조각으로 내보냅니다. 앱이 쉬지 않아도 50ms 마다 한 조각은 돌아 큐가 끝없이 쌓이지 않습니다. `requestIdleCallback` 이 없는 브라우저(Safari)도 같은 간격으로 돕니다.
- **Web Worker 는 쓰지 않습니다.** fiber 와 응답 객체처럼 앱이 가진 객체 자체를 다뤄야 해서 다른 스레드로 넘길 수 없습니다.
- **큐를 그 자리에서 비우는 곳은 정해져 있습니다.** 사용자 조회(요소 클릭, 요청 상세, 요청 행 마우스 강조, 보고서)와 페이지를 떠날 때 기록 저장, 보고서 저장 전 소스맵 대기뿐입니다. 주기적으로 도는 화면은 그때까지 분석된 것만 보여 줍니다.

### 4.11 판정 기준을 코드로 정하기(configure)

판정 기준(중복 2초, 몰림 500ms·5건, 기억할 요청 200건)과 보고서 경로, 팀이 함께 쓸 무시 목록, 같은 요청 판정에 넣을 헤더는 `configure()` 로 정합니다(#78). 패널에서 고른 무시는 사람마다 localStorage 에만 남아 팀이 함께 쓰지 못했습니다.

- **prop 이 아니라 함수입니다.** 요청은 컴포넌트 mount 전에 나가므로(import 시점 설치) `<RdxDevtools>` 의 prop 으로 받으면 그 전 요청에 적용되지 않습니다. 판정은 유휴 큐에서 하므로 import 바로 뒤에 부르면 그 전에 나간 요청도 새 기준으로 판정합니다. 보고서 경로 확인도 한 마이크로태스크 미뤄 같은 틱의 `configure({ reportPath })` 를 따릅니다.
- **설정 파일(`rdx.config.ts`)은 두지 않았습니다.** 번들러마다 읽는 방법이 달라서입니다.
- **값은 전역 설정 객체 하나에서 읽습니다(`core/config.ts`, `Symbol.for('react-data-xray.config')`).** rdx 가 두 벌 평가되면 처음 것만 설치되므로(#79), 어느 사본의 `configure` 든 설치된 사본에 닿게 전역에 둡니다. 앱 경로(fetch/XHR)에는 일이 늘지 않습니다. `keyHeaders` 도 이미 기록한 요청 헤더에서 요청 키를 만들 때(유휴 큐) 몇 개 더 읽을 뿐이고, 정하지 않으면 키가 예전과 같습니다. 엔드포인트 집계 단위는 그대로이고 같은 요청(중복·같은 응답) 판정만 나뉩니다. React Query 캐시키 점검의 "키에 빠진 파라미터" 는 헤더를 뺀 키(`paramKeyOf`)로 봅니다. 헤더만 다른 요청은 URL·본문의 파라미터가 빠진 것이 아니기 때문입니다. "같은 요청을 다른 키로 캐시" 는 헤더까지 본 키로 봐서, 테넌트별 키를 중복 캐시로 잡지 않습니다.
- **부를 때마다 기본값 위에 통째로 바꿉니다.** 같은 값으로 여러 번 불러도(HMR) 같고, 맞지 않는 값은 경고하고 기본값을 씁니다. `maxRecords` 는 5000 까지입니다(요청마다 응답 원문을 붙듭니다). production 빌드에서는 빈 함수입니다(`RdxDevtools` 와 같은 방식).
- **설정이 바뀌면 다시 그립니다.** `configure` 마다 번호(`configVersion`)가 오르고 구독자에게 알립니다. 패널의 무시 판정(`useIgnoredEndpoints`)이 번호로 새로 만들어져 분류와 요청 탭 표시가 같은 기준을 씁니다.
- **새로고침 전 기록은 그때의 상한으로 자릅니다.** 기록은 import 할 때 되살려 `configure` 보다 먼저 들어오므로, 합칠 때 자르지 않고 유휴 큐(또는 다음 응답)에서 그때의 `maxRecords` 로 자릅니다. 되살린 기록은 버려도 `dropped` 로 세지 않습니다.
- **코드의 무시는 패널의 무시와 합쳐 보지만 따로 둡니다.** 판정은 한 곳(`shared/ignoredEndpoints.ts` 의 `IgnoreMatcher`)에서 만들어 분류·보고서·요청 탭이 같이 쓰고, 엔드포인트마다 한 번만 계산합니다. 문자열은 엔드포인트 이름과 정확히 같아야 하고(저장된 무시처럼 ID 는 `:id` 로 묶음), 정규식은 이름에 맞춰 봅니다. 패널에서는 "Ignored (config)" 로 보여 풀 수 없게 합니다. 코드에서 정한 것을 화면에서 풀면 다음 새로고침에 되살아나 헷갈립니다.
- **보고서에 적용된 설정(`config`)을 남기고, compare 는 판정 기준이 다른 두 보고서를 경고합니다.** 기준이 다르면 중복 수 증감을 믿을 수 없습니다. `config.ignore` 는 코드와 패널의 무시를 나눠 담아 패널 무시가 바뀐 것도 보입니다. 경고는 판정 기준(`dedupeWindowMs`, `burst`, `keyHeaders`, 순서와 무관한 `ignore`)만 보고, `reportPath` 는 보지 않으며, `maxRecords` 는 어느 한쪽이라도 버린 요청이 있을 때만 봅니다. 설정을 남기기 전에 저장한 스냅샷과는 비교하지 않습니다.
- **보고서 경로는 브라우저와 dev 서버가 같아야 합니다.** 브라우저는 `configure({ reportPath })`, dev 서버는 `rdx({ path })`·`rdxReportMiddleware(root, { path })` 로 정합니다. Next.js route 는 경로를 보지 않고 Next 가 내보내는 곳(`basePath` 면 `<basePath>/__rdx/report`)에서 답하므로 브라우저 쪽만 정합니다. 경로가 바뀌면 브라우저는 그 경로를 다시 확인한 뒤에만 보냅니다(확인하지 않은 경로로 snapshot 을 보내지 않습니다).
- UI 쪽 설정(`initialOpen`, 버튼 위치, `disabled`)은 이번에 넣지 않았습니다.

## 5. 화면 구성

툴바의 중심은 두 축입니다. **대상**은 무엇을 볼지, **관점**은 그 대상의 무엇을 볼지입니다. 사용자는 대상 하나를 고르고 관점만 바꿔 가며 같은 컴포넌트를 데이터·네트워크·렌더 쪽에서 봅니다. 여기에 **측정**과 **창** 묶음을 더해 네 묶음을 구분선으로 나누고, 창 묶음은 늘 오른쪽 끝에 둡니다.

화면과 보고서 문구는 영어입니다. 아래 표는 기능을 한국어로 부릅니다(대상의 화면 전체는 `Whole page`, 요소 선택은 `Pick element`). 한국어 화면 선택은 #45 에서 다룹니다.

| 구성 | 하는 일 |
|---|---|
| 플로팅 `RDX` 버튼 | 드래그로 옮기고 위치를 기억합니다(창 밖으로 나가면 안으로 당깁니다). 문제 수(낭비 요청이 있는 엔드포인트 + 렌더 폭주 컴포넌트)를 배지로 달고, 새 요청 몰림이나 새 렌더 폭주가 생기면 1초 동안 색이 바뀝니다. 배지 내역에서 무엇을 세었는지 보고, 항목을 누르면 그 탭의 그 줄로 갑니다. 키보드로도 엽니다. |

## 6. 알려진 한계

- React 내부 구조(fiber, 훅 체인, 플래그)는 공개 API가 아닙니다. React가 구조를 바꾸면 깨질 수 있습니다.
- 파생 매칭은 필드 값 겹침으로 판단해서, 같은 값을 가진 다른 응답을 가리킬 수 있습니다.
- context 는 값과 바로 아래 한 단계까지만 봅니다. 그보다 깊이 품은 응답은 출처로 잡지 않습니다.
- 박스는 응답 객체를 props 로 받는 컴포넌트에만 그립니다. state 로만 들고 있는 컴포넌트는 요소 선택과 "이 요청의 데이터를 쓰는 컴포넌트"로 찾습니다.
- 소스맵은 http 로 받을 수 있는 모듈에만 적용합니다(Vite dev). webpack 의 eval 소스맵(`webpack-internal://`)은 바꾸지 않습니다.
- 큰 소스맵의 `JSON.parse` 한 번은 조각으로 나눌 수 없어 메인 스레드에 남습니다.
- 최근 요청 200건(`configure` 의 `maxRecords`)만 기억합니다.
- 화면 이동은 rdx 가 감싼 `history.pushState`·`replaceState` 로 압니다. rdx 보다 먼저 실행된 코드가 원래 메서드를 따로 잡아 두고 부르면 그 이동은 보지 못합니다. rdx 는 앱 코드보다 먼저 import 해야 하므로 실제로는 드뭅니다.
- 렌더 수는 React 내부 플래그로 세므로 실제와 조금 다를 수 있습니다.
- 레이아웃 이동은 Chromium 계열 브라우저에서만 봅니다(Safari·Firefox 는 layout-shift 항목을 주지 않습니다). 원인은 먼저 밀린 컴포넌트와 그 조상의 렌더로 찾습니다. 위쪽 형제가 커져 아래 컴포넌트가 밀린 경우는 거기서 찾지 못해, 이동 직전에 응답으로 렌더된 commit 으로 짐작합니다(`inferred`). 같은 1초 안에 서로 다른 응답으로 렌더된 commit 이 여럿이면 엉뚱한 응답을 가리킬 수 있습니다.
- "같은 내용 새 참조"는 JSON으로 비교하므로 Map, Set, 클래스 인스턴스, 순환 참조, 20KB를 넘는 값은 다르다고 봅니다(줄일 수 있는 렌더를 놓칠 수 있음).
- 클래스 컴포넌트의 `forceUpdate`는 "부모 렌더"로 분류됩니다.
- 쓰지 않는 응답(`unused`)은 응답 3초 뒤 컴포넌트의 props·훅 state·context 에 응답 객체(또는 필드 값이 겹치는 가공 객체)가 있는지로만 봅니다. 데이터를 effect·이벤트 핸들러에서만 쓰거나(ref, 모듈 변수, 로그), 가공해 원래 필드 값이 남지 않는 새 객체로 만들거나(합계, 개수, 이름을 바꾼 필드), 3초 안에 화면을 떠나 쓰던 컴포넌트가 사라지면 쓰지 않는 것으로 보입니다. 3초보다 늦게 그리는 응답도 그렇습니다. 그래서 노랑(확인 필요)입니다. GraphQL 조회처럼 POST 로 보내는 조회는 변경 요청과 함께 판정에서 빠집니다.
- 렌더의 네트워크 원인은 응답 객체를 그대로 쓸 때만 찾습니다. 응답을 가공해 새 객체로 만들면(map, select 등) 네트워크와 무관으로 보일 수 있습니다.
- 요청 헤더는 `configure({ keyHeaders })` 로 정한 것만 비교합니다. 정하지 않으면 헤더만 다른 요청은 같은 요청으로 봅니다. 새로고침 전 기록은 인증 헤더 값을 가려 저장하므로, 그런 헤더를 keyHeaders 에 넣으면 되살린 기록끼리만 같은 값으로 묶입니다.
- 주기 요청은 같은 요청이 3번 쌓여야 알아봅니다. 그 전까지(첫 두 번)는 낭비로 보일 수 있습니다.
- StrictMode 재실행 확인은 effect 안에서 바로(await 전에) 요청을 보낼 때만 호출 스택으로 됩니다. await 뒤에 보내면 앞 요청을 cleanup 에서 취소할 때만, 그리고 두 요청이 마운트한 commit 의 순번에 남을 때(재실행은 같은 passive effect 비우기 안에서 일어나 대개 그렇습니다)만 알아봅니다. 렌더 기록이 있는 commit 이면 보낸 컴포넌트를 스택의 첫 앱 프레임 파일 이름(`Profile.tsx`)으로만 알 수 있어, 컴포넌트 파일이 아니면 중복으로 잡힙니다. 반대로 렌더 기록이 없는 commit(감시를 켜기 전)에서 마운트 직후 핸들러가 200ms 안에 같은 요청을 취소하고 다시 보내면 StrictMode 로 보입니다.
- React Query의 structural sharing 때문에 다시 받아 온 데이터라도 바뀌지 않은 객체는 처음 요청이 출처로 표시됩니다.
- 응답 경로가 `$`(응답 전체)인 매칭은 "이 API 어딘가"라는 뜻입니다. 요소를 누르면 누른 글자로 필드까지 좁히지만, 같은 값이 여러 곳에 있으면 좁히지 않습니다.
- ESM 전용 패키지라 CJS 모드 Jest(babel-jest 기본 설정)는 불러오지 못합니다. `exports` 에 `default` 조건을 둬 해석은 되지만, `import.meta.url` 이 있어 `transformIgnorePatterns` 로 변환해도 CJS 로 실행되지 않습니다. README 에 `moduleNameMapper` 로 빈 모듈을 쓰는 방법을 적었습니다. CJS 빌드를 함께 내지 않는 것은 두 벌이 함께 로드되면 가로채기가 두 번 설치되기 때문입니다. `import.meta.url` 을 호출 스택에서 구한 값으로 바꾸면 변환은 되지만, 스택 형식이 엔진·번들러마다 달라(Firefox·Safari 는 첫 줄이 프레임, Node CJS 는 URL 이 아닌 경로, webpack eval 은 `webpack-internal://`, 앱이 `Error.stackTraceLimit = 0` 으로 두면 프레임 없음) rdx 자신의 프레임을 빼는 규칙이 틀어질 수 있어 두었습니다.
- ESM 전용이라 `"type": "module"` 이 아닌 TypeScript CJS 프로젝트(`module: node16`)는 타입도 가져오지 못합니다(TS1479). 바꾸지 않았습니다.

품질 도구: oxlint(정적 검사), oxfmt(포맷), react-doctor(React 진단), vitest 커버리지(80% 이상). `pnpm check` 가 모두 돌립니다.

`package.json` 의 `sideEffects` 는 `false` 가 아니라 모듈 최상위에서 설치하는 파일(`dist/index.js`, `dist/core/render/monitor.js`)과 최상위에서 `main()` 을 부르는 CLI 실행 파일(`dist/cli/bin.js`)의 목록입니다. 실행 파일은 라이브러리의 import 그래프에 없어 번들에는 들어가지 않습니다. 검사 스크립트에서 빼는 대신 목록에 넣은 것은, 최상위 부수 효과가 있는 파일은 목록에 있다는 검사의 규칙을 예외 없이 지키기 위해서입니다. `false` 면 Next.js `instrumentation-client.ts` 처럼 이름 없이 `import 'react-data-xray'` 만 둔 곳을 번들러가 지워, 요청 가로채기·렌더 감시가 조용히 꺼집니다(#61). production 은 설치 코드가 `NODE_ENV` 분기 안에 있어 목록과 상관없이 비워집니다. `pnpm check:side-effects`(CI)가 dist 의 최상위 문장을 읽어 목록과 맞는지, 단독 import 를 rolldown 으로 묶어 dev 에 남고 production 이 비는지 봅니다.

Vite 플러그인의 `inject: true` 는 dev 서버가 내보내는 `index.html` 에 `<script type="module">import 'react-data-xray'</script>` 를 넣어 진입 import 를 대신합니다(#79). `head-prepend` 지만 Vite 의 client·React Refresh 프리앰블보다는 뒤이고 앱의 진입 모듈보다는 앞입니다. 켠 경우에만 훅을 달아 끈 사용자는 Vite 3 이하에서도 전과 같고, Vitest 와 Storybook `iframe.html` 에는 넣지 않으며, Vite 가 HTML 을 내보내지 않는 SSR·백엔드 연동에서는 효과가 없습니다. 모노레포 등에서 rdx 가 두 벌 평가되면 `globalThis[Symbol.for('react-data-xray.installed')]` 표식을 본 두 번째 사본이 설치를 건너뛰고 한 번 경고합니다(모듈 상태가 따로라 각 설치 함수의 가드로는 막지 못합니다). `transformIndexHtml` 을 `order: 'pre'` 로 두는 것은 Vite 가 인라인 모듈 스크립트를 html-proxy 모듈로 바꾸고 맨 이름 import 를 사전 번들 경로로 해석하는 단계보다 먼저 넣어야 하기 때문입니다. 진입 파일의 `import { RdxDevtools } from 'react-data-xray'` 와 같은 URL 이 되어 모듈은 한 번만 평가됩니다(`optimizeDeps.exclude` 로 둔 경우도 같습니다). 기본값을 끈 것은 사용자가 모르는 사이 앱의 HTML 을 바꾸지 않기 위해서이고, 플러그인은 `apply: 'serve'` 라 production 빌드에는 붙지 않습니다.

## 8. 개발 기록

- 패키지 위치: `~/Project/react-data-xray`. 커밋은 개인 계정으로 합니다.
- whatap-front 테스트: `.worktrees/rdx` 워크트리(브랜치 `local/react-data-xray`)에 `file:` 의존성으로 붙여 확인합니다. whatap-front 쪽 변경은 커밋하지 않습니다.
- 패키지를 고치면 `pnpm sync <앱 경로>` 로 빌드·반영합니다. 앱의 `vite.config` 에서 rdx 를 `optimizeDeps.exclude` 에 넣고 `server.watch` 로 감시하면 dev 서버를 다시 띄우지 않아도 페이지가 새 코드로 다시 열립니다. 서버 쪽 코드(미들웨어)를 바꿔 dev 서버를 다시 띄웠다면, 띄운 **뒤에** `pnpm sync` 를 한 번 더 합니다(같은 버전의 `?v=` 해시로 브라우저가 이전 모듈을 쓰지 않게).
- 성능은 실제 앱에서 PerformanceObserver(longtask)로 잽니다. 잴 때는 새 코드가 로드됐는지(모듈 URL 의 `?t=`) 먼저 확인합니다.
- 기능마다 code-review(high)와 ponytail 감사를 돌려 지적을 고친 뒤 다음으로 넘어갔습니다.
- 감사 기록: 코드 감사(구현과 문서 대조)와 문제 해결 적합성 평가를 서브에이전트로 따로 했습니다. 코드 감사에서 나온 버그(파생 매칭 기준, 이전 fiber 트리 읽기, 오버레이 비용, XHR 재사용, 스트리밍 버퍼링, 경로 접두사 비교, 렌더 첫 commit 과다 집계, webpack production 잔존)는 고쳤습니다. 적합성 평가의 개선 제안은 ROADMAP에 넣었습니다.
